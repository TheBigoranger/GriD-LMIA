\begin{abstract}
This manual describes the current public behavior of the \pkg.  The package
uses \code{dpbase} as the backend parent for cell-local Bernstein coefficient
storage, provides \code{dpmat} for known finite real matrix functions on tensor
grids, provides \code{dpvar} for YALMIP-backed Bernstein decision expressions
and \code{rhodiff} derivatives, and provides \code{dplmi} for direct
coefficient-wise YALMIP constraint assembly.  The manual is written as a
reference manual: conceptual Bernstein material comes first, and each class
chapter then documents supported call forms, arguments, outputs, examples, and
limits.
\end{abstract}

\section{Bernstein And Grid Background}
\label{sec:bernstein}

\subsection{From Approximation Theory To DP-LMIs}
\label{sec:bernstein-history}

Bernstein introduced this polynomial basis in 1912 in a constructive proof of
the Weierstrass approximation theorem.  The same control-point representation
later became central to B\'ezier curves and the de Casteljau algorithm
\cite{farouki2012}.  For this package, however, the important bridge to control
is not approximation alone.  It is the combination of four facts:
nonnegative basis functions, a partition of unity, tensor-product coordinates
on boxes, and exact coefficient algebra.  Together they turn a matrix
polynomial on each physical cell into a convex combination of finitely many
matrix coefficients.

This viewpoint separates three layers that are easy to conflate.  A physical
grid divides the scheduling domain into cells.  A Bernstein basis represents a
polynomial exactly inside each cell.  Finally, \code{dplmi} converts a
matrix-sign requirement into finitely many sufficient coefficient constraints.
The first two layers are representation; the third is a certificate.

\subsection{Local Coordinates And Degree-Two Coefficients}
\label{sec:bernstein-local}

On one physical interval \([\rho_i,\rho_{i+1}]\), the package uses the local
coordinate
\[
  a = \frac{\rho_{i+1}-\rho}{\rho_{i+1}-\rho_i}.
\]
Thus \(a=1\) at the lower endpoint and \(a=0\) at the upper endpoint.  A
degree-\(m\) Bernstein polynomial on that cell is
\[
  P(\rho) =
  \sum_{j=0}^{m} \binom{m}{j} a^{m-j}(1-a)^j C_j.
\]
Write
\[
  B_j^m(a)=\binom{m}{j}a^{m-j}(1-a)^j.
\]
On \(0\le a\le1\), every \(B_j^m(a)\) is nonnegative and
\[
  \sum_{j=0}^{m}B_j^m(a)=(a+(1-a))^m=1.
\]
Thus the Bernstein basis is a nonnegative partition of unity.  It also
interpolates the cell endpoints in the package ordering:
\(P(\rho_i)=C_0\) and \(P(\rho_{i+1})=C_m\).  Many references instead use
\(t=(\rho-\rho_i)/(\rho_{i+1}-\rho_i)=1-a\).  Their forward-index formulas
describe the same basis, but endpoint labels must be reversed before comparing
coefficients with \code{LocalValues}.

The degree-two case is the first case where the middle Bernstein scale matters:
\[
  P(\rho)=a^2 C_0+2a(1-a)C_1+(1-a)^2 C_2.
\]
The package stores the coefficient matrices \(C_0,C_1,C_2\), not sampled values
of the expanded monomial form.  For matrix-valued objects, each \(C_j\) is a
finite real matrix for \code{dpmat}, or a YALMIP affine matrix expression for
\code{dpvar}.

For tensor grids, a local Bernstein coefficient label is a row vector.  For
example, a two-parameter degree-one cell has labels
\([0,0]\), \([0,1]\), \([1,0]\), and \([1,1]\).  Each label selects one
tensor-product Bernstein basis term, one local index per parameter direction.

For \(\ell\) parameters, the tensor-product basis is
\[
  B_{\boldsymbol j}^{m}(\boldsymbol a)
  =\prod_{r=1}^{\ell}B_{j_r}^{m}(a_r).
\]
Its terms are again nonnegative and sum to one because
\[
  \sum_{\boldsymbol j}B_{\boldsymbol j}^{m}(\boldsymbol a)
  =\prod_{r=1}^{\ell}\sum_{j_r=0}^{m}B_{j_r}^{m}(a_r)=1.
\]
The package uses this box, or hyperrectangular, tensor product.  Bernstein
bases on simplices are mathematically related, but they are not the storage
convention implemented by \code{dpbase}.

\subsection{Reading A Gridding Input}
\label{sec:bernstein-gridding-input}

The word ``grid'' has two independent meanings in a Bernstein model, and it
is important not to exchange them.  The input grid vectors choose the physical
cell boundaries; \code{Degree=m} chooses the polynomial degree \emph{inside
every one} of those cells.  Thus, a one-dimensional vector
\code{[0 0.4 1]} creates two physical intervals, regardless of whether
\code{Degree} is zero, one, two, or higher.  With \(q_r=N_r-1\) physical
cells in parameter direction \(r\), a continuous global coefficient grid for
degree \(m\) has
\[
  q_r m+1
\]
coefficient payloads in that direction.  These payloads are Bernstein
coefficients, not automatically samples of the represented function.

constructor accepts every nonnegative integer \code{Degree}; in particular,
\code{dpvar(1, grid)} creates the continuous degree-one decision function over
the same two physical cells, while higher degrees share every control matrix on

grid = {[0 1 2], [10 20 30]};    % 2-by-2 physical cells

% A.coeffs([1 1]) is {11, 12, 21, 22}
\end{lstlisting}

More generally, an \(\ell\)-parameter input is a cell vector containing one
strictly increasing physical node vector per parameter.  It defines
\(\prod_{r=1}^{\ell}(N_r-1)\) hyperrectangular physical cells.  A common
degree \(m\) creates \((m+1)^\ell\) local Bernstein coefficients in each
cell, while a continuous global coefficient array has size
\([\,(N_1-1)m+1,\ldots,(N_\ell-1)m+1\,]\).  The package enumerates local
labels such as \([0,0,\ldots,0]\) and \([m,m,\ldots,m]\) in tensor order;
the global array shares the corresponding coefficients on every common cell
face.  Increasing the number of physical cells refines the parameter domain;
increasing \code{Degree} increases the polynomial order within each cell.
Neither operation should be interpreted as the other.

\subsection{Convex Hulls And Matrix Sign Certificates}
\label{sec:bernstein-convex-hull}

The partition-of-unity identity makes every value a convex combination of its
coefficient data:
\[
  P(\boldsymbol a)=
  \sum_{\boldsymbol j}B_{\boldsymbol j}^{m}(\boldsymbol a)C_{\boldsymbol j}
  \in \operatorname{conv}\{C_{\boldsymbol j}\}.
\]
For a scalar polynomial this gives the range enclosure
\[
  \min_{\boldsymbol j}C_{\boldsymbol j}
  \le P(\boldsymbol a)\le
  \max_{\boldsymbol j}C_{\boldsymbol j}.
\]
For symmetric matrices, apply the same identity to an arbitrary vector \(x\):
\[
  x^{\mathsf T}P(\boldsymbol a)x
  =\sum_{\boldsymbol j}B_{\boldsymbol j}^{m}(\boldsymbol a)
    x^{\mathsf T}C_{\boldsymbol j}x.
\]
Consequently, \(C_{\boldsymbol j}\preceq0\) for every local label is sufficient
for \(P(\boldsymbol a)\preceq0\) throughout the cell; the positive-semidefinite
statement is analogous.  If all finitely many coefficients are strictly
negative definite, their smallest eigenvalue margins also give a uniform
strict certificate on the cell.

The implication is one-way.  A matrix polynomial may be negative definite at
every point even though one Bernstein coefficient is not.  A failed direct
coefficient test therefore does not establish infeasibility of the continuous
DP-LMI.  This distinction is the central source of conservatism in direct
Bernstein assembly and is already present in Bernstein range tests used for
interval-parameter robustness \cite{zettler1998}.

\subsection{Multiplication, Degree Growth, And Convolution}
\label{sec:bernstein-product}

Multiplication raises Bernstein degree.  In one parameter, multiplying two
degree-one factors gives a degree-two product:
\[
  \bigl(a A_0 + (1-a)A_1\bigr)
  \bigl(a B_0 + (1-a)B_1\bigr)
  =
  a^2 A_0B_0
  + a(1-a)(A_0B_1 + A_1B_0)
  + (1-a)^2 A_1B_1.
\]
Because the degree-two Bernstein middle basis is \(2a(1-a)\), the stored middle
coefficient is \((A_0B_1 + A_1B_0)/2\).

This is not a special rule for linear factors.  If \(B_i^m(a)\) denotes the
\(i\)-th Bernstein basis function of degree \(m\), then
\[
  B_i^m(a) B_j^n(a)
  =
  \frac{\binom{m}{i}\binom{n}{j}}{\binom{m+n}{i+j}}
  B_{i+j}^{m+n}(a).
\]
For coefficient arrays this is a convolution over coefficient labels.  In one
parameter,
\[
  C_k
  =
  \sum_{\substack{i+j=k\\0\le i\le m,\ 0\le j\le n}}
  A_i B_j
  \frac{\binom{m}{i}\binom{n}{j}}{\binom{m+n}{k}},
  \qquad k=0,\ldots,m+n.
\]
In \(\ell\) parameters, replace the scalar labels \(i,j,k\) by multi-indices
\(\alpha,\beta,\gamma\), use \(\alpha+\beta=\gamma\), and multiply the binomial
scale over parameter directions:
\[
  C_\gamma =
  \sum_{\alpha+\beta=\gamma}
  A_\alpha B_\beta
  \prod_{r=1}^{\ell}
  \frac{\binom{m}{\alpha_r}\binom{n}{\beta_r}}
       {\binom{m+n}{\gamma_r}}.
\]
This is the coefficient rule used by \code{dpmat * dpmat} and by supported
known-data products involving \code{dpvar}.  Matrix order is preserved inside
every convolution term: in general \(A_\alpha B_\beta\neq
B_\beta A_\alpha\), so exchanging the operands changes both the algebra and the
resulting coefficient matrices.

\subsubsection{Weighted Value-Grid Convolution}
\label{sec:bernstein-weighted-convolution}

The same rule can be read as an ordinary \(\ell\)-dimensional discrete
convolution.  First reshape one cell's flat coefficient lists into value grids
indexed by \(\boldsymbol\alpha\in\{0,\ldots,m\}^\ell\) and
\(\boldsymbol\beta\in\{0,\ldots,n\}^\ell\), using the same order as
\code{lbls}.  Restore the binomial weights carried by the Bernstein basis:
\[
  \widetilde A_{\boldsymbol\alpha}
  =
  A_{\boldsymbol\alpha}
  \prod_{r=1}^{\ell}\binom{m}{\alpha_r},
  \qquad
  \widetilde B_{\boldsymbol\beta}
  =
  B_{\boldsymbol\beta}
  \prod_{r=1}^{\ell}\binom{n}{\beta_r}.
\]
These weighted value grids multiply by ordered discrete convolution:
\[
  \widetilde C_{\boldsymbol\gamma}
  =
  \bigl(\widetilde A *_\ell \widetilde B\bigr)_{\boldsymbol\gamma}
  =
  \sum_{\boldsymbol\alpha+\boldsymbol\beta=\boldsymbol\gamma}
  \widetilde A_{\boldsymbol\alpha}
  \widetilde B_{\boldsymbol\beta}.
\]
Finally, divide out the degree-\(m+n\) Bernstein weights to return to stored
coefficients:
\[
  C_{\boldsymbol\gamma}
  =
  \frac{\widetilde C_{\boldsymbol\gamma}}
       {\displaystyle\prod_{r=1}^{\ell}
        \binom{m+n}{\gamma_r}}.
\]
Combining these three lines recovers the binomial-scaled coefficient formula
above.  On a tensor grid, multiplication raises the common Bernstein
\code{Degree} from \(m\) and \(n\) to \(m+n\) in every local parameter
direction, so one cell contains \((m+n+1)^\ell\) output coefficients.  For
matrix values, \(*_\ell\) is an ordered convolution: the left grid entry always
multiplies the right grid entry in that order.

\subsection{Degree Elevation And Polynomial Representation}
\label{sec:bernstein-elevation}

A polynomial represented in Bernstein degree \(m\) can also be represented in
any higher degree \(M\ge m\).  In one parameter, the elevated coefficient
\(\widehat C_k\) of degree \(M\) is
\[
  \widehat C_k =
  \sum_{i=\max(0,k-(M-m))}^{\min(m,k)}
  C_i
  \frac{\binom{m}{i}\binom{M-m}{k-i}}{\binom{M}{k}},
  \qquad k=0,\ldots,M.
\]
Tensor grids apply the same formula by tensor product over each parameter
direction.  The package uses degree elevation when two coefficient-backed
objects with the same grid bounds but different Bernstein degree must be
combined by addition, subtraction, concatenation, assignment, or other
coefficient-wise operations.

Degree elevation does not change the polynomial or add decision freedom.  Each
elevated coefficient is a convex combination of old coefficients, and repeated
elevation makes the coefficient polygon track the represented function more
closely \cite{farouki2012}.  This is different from constructing a new decision
function with a higher degree.  The public \code{dpvar} constructor accepts
every nonnegative integer degree; products may produce still higher-degree
expressions, which are aligned internally by \code{bernElev}.

\subsection{Differentiation And de Casteljau Subdivision}
\label{sec:bernstein-differentiation}

The reversed local coordinate changes the intermediate sign in a derivative.
For cell width \(h=\rho_{i+1}-\rho_i\), the two sign reversals combine to give
the forward physical difference
\[
  \frac{dP}{d\rho}
  =\frac{m}{h}\sum_{j=0}^{m-1}
    (C_{j+1}-C_j)B_j^{m-1}(a).
\]
This is the scalar-cell formula behind \code{rhodiff}.  In several scheduling
dimensions, the directional rate term is
\(
  \dot P=\sum_{r=1}^{\ell}(\partial P/\partial\rho_r)\dot\rho_r
\).
The implementation forms each cell-local partial difference, elevates partials
to a common tensor degree when necessary, and evaluates the affine rate
dependence at all active \(\dot\rho\)-box vertices.  Derivative boundary rows
remain cell-local rather than sharing the continuous coefficient handles of
the original \code{dpvar}.

The de Casteljau recursion evaluates the same polynomial through neighboring
affine combinations:
\[
  C_j^{(r)}=aC_j^{(r-1)}+(1-a)C_{j+1}^{(r-1)},
  \qquad C_j^{(0)}=C_j.
\]
Its edge chains also give exact Bernstein coefficients on the two subintervals
created at the split point.  Applying this one-dimensional operation along
each parameter axis gives exact tensor-product subdivision.  Subdivision is
therefore a useful certificate-refinement idea: the polynomial is unchanged,
but its convex hulls are recomputed on smaller physical cells.  The current
package does not expose a general public de Casteljau or adaptive-subdivision
API; these facts explain the representation and future refinement direction,
not an implemented call form.

\subsection{Storage And Hypercube Traversal}
\label{sec:bernstein-storage}

The physical grid and the local Bernstein labels are separate.  For
\(\ell\) parameters with node counts \(N_1,\ldots,N_\ell\), the number of
physical hypercubes is
\[
  \prod_{r=1}^{\ell}(N_r-1).
\]
For Bernstein degree \(m\), each physical hypercube stores
\[
  (m+1)^\ell
\]
local coefficients.  The helper ordering used by \code{cells} and \code{lbls}
is lexicographic with earlier dimensions varying more slowly.

Physical cells are stored as nested \code{LocalValues} entries, indexed by one
physical-cell subscript per scheduling dimension.  The selected entry is a
flat coefficient cell in local label order.
For a continuous \code{dpvar}, adjacent cells reuse the symbolic handles on
their common face; continuity is therefore encoded by coefficient sharing,
not by adding equality LMIs.  Known \code{dpmat} data follow the same
cell-local layout.  Discontinuous derivative objects intentionally keep
separate boundary entries so each cell retains its own physical-width and
rate-vertex derivative data.

\examplehead
The storage counts follow directly from the physical grid and the local
Bernstein degree.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1 2], [10 20]}, {1 2; 3 4; 5 6}, Degree=1);
A.ncell()
A.ncoeff()
A.npar()
\end{lstlisting}

\begin{lstlisting}[style=dpoutput]
ans =
     2

ans =
     4

ans =
     2
\end{lstlisting}

\subsection{Conservatism And Refinement Hierarchy}
\label{sec:bernstein-refinement}

When a coefficient-wise LMI fails, the following distinctions keep the next
modeling step precise:

\begin{enumerate}[leftmargin=*]
  \item The failure proves only that the present sufficient certificate did
        not succeed; it does not prove the continuous DP-LMI infeasible.
  \item Physical cell subdivision restricts and reparameterizes the same
        polynomial on smaller cells, usually tightening local convex hulls.
  \item Pure degree elevation preserves exactly the same polynomial and
        decision variables.  A genuinely higher-degree decision
        parameterization instead enlarges the search space.
  \item The optional cell-local Polya mode is degree elevation followed by the
        same coefficient-wise constraints.  It does not introduce auxiliary
        variables or change the stored residual; broader vertex-pair and
        sum-of-squares constructions remain separate sufficient hierarchies.
\end{enumerate}

Spline-type parameter-dependent LMI methods give important motivation for
partition refinement.  Masubuchi, Kume, and Shimemura derived finite local LMI
conditions and an asymptotic refinement result under the assumptions of their
formulation \cite{masubuchi1998}.  Xu and Jabbari continued the grid/spline
line in parameter-varying output-feedback synthesis and improved
\(L_2\)-gain computation \cite{xu2024}.  These results motivate the package's
cell-local architecture, but they are not a blanket completeness theorem for
every package mode.

\subsection{Control Context And The Implemented Boundary}
\label{sec:bernstein-control-context}

The literature places this representation among several complementary
polynomial-control certificates.  Zettler and Garloff used multivariate
Bernstein expansion and convex-hull bounds for robustness analysis of
polynomial families with interval parameters \cite{zettler1998}.  Chesi's
survey situates coefficient tests beside broader LMI techniques for polynomial
optimization in control, including homogeneous and sum-of-squares approaches
\cite{chesi2010}.  The present package is related to that lineage, but its
cell-local tensor storage and rate-vertex assembly are project-specific.

The implemented public boundary is deliberately narrower than this background:

\begin{itemize}[leftmargin=*]
  \item \code{dpbase} provides backend Bernstein storage, degree elevation,
        and product convolution used by \code{dpmat} and \code{dpvar}.
  \item \code{rhodiff} forms the implemented rate-affine derivative rows, and
        \code{dplmi} directly constrains every active rate row and local
        coefficient before \code{toYalmip} hands the model to YALMIP.
  \item \code{dplmi} also implements opt-in cell-local P\'olya degree
        elevation before coefficient assembly. Relaxation-lemma assembly,
        sum-of-squares machinery, adaptive subdivision, package-owned
        strictness margins, residual certificates, and diagnostic hierarchies
        are not current public APIs. In particular, \code{relaxLemma=true} is
        rejected rather than silently approximated.
\end{itemize}

\subsubsection{\texorpdfstring{\code{elevVals}}{elevVals}}
\label{sec:dpbase-elevvals}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
vals = obj.elevVals(degreeIncrement)
\end{lstlisting}

\arghead
\begin{itemize}[leftmargin=*]
  \item \code{degreeIncrement} is a finite nonnegative integer scalar.  It is
        added to \code{obj.Degree} in every parameter direction; zero returns
        coefficient evidence at the current degree.
\end{itemize}

\refhead{Output}
\code{vals} is a nested \code{LocalValues}-shaped cell tree.  Each physical
cell contains coefficients of degree \code{obj.Degree + degreeIncrement}, with
the represented polynomial, physical-cell tree, and any rate-row ordering
preserved.  The method does not modify \code{obj} or its stored coefficient
evidence.

\refhead{Validation and errors}
An invalid increment raises \code{dpbase:InvalidDegreeIncrement}.  A
function-only \code{dpmat} has no stored Bernstein coefficient evidence, so
this method raises \code{dpbase:MissingCoefficientEvidence}.

\textit{Relationship to backend and public algebra.}  Unlike protected
\code{bernElev}, which elevates one flat cell coefficient family for internal
alignment, \code{elevVals} is a public whole-object query returning elevated
\code{LocalValues}.  Public coefficient algebra uses \code{bernElev}
internally when compatible operands need degree alignment; it does not mutate
either operand.

        Bernstein coefficients, or explicit nested \code{LocalValues}; for
        example, \code{{1, 2, 3}} is scalar degree-two data on one cell.
  \item \code{Degree=m} sets the local Bernstein degree.  For function handles,
        omitting \code{Degree} creates a function-only object; passing a value
        such as \code{Degree=2} validates and stores Bernstein coefficient
        evidence while retaining the exact function handle for \code{evaluate}.
\end{itemize}

\examplehead
The scalar-grid shorthand is the shortest coefficient-backed form.  The three
numeric cells below are the global Bernstein coefficients for two physical
cells with degree one.

\begin{lstlisting}[style=dpmatlab]

size(A)
A.Degree
A.SourceSummary
\end{lstlisting}

ans =
     1

ans =
    "coefficient-backed"
\end{lstlisting}

\begin{lstlisting}[style=dpmatlab]

\subsection{\texorpdfstring{\code{evaluate}}{evaluate}}
\label{sec:dpmat-evaluate}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
val = evaluate(A, point)
val = A.evaluate(point)
\end{lstlisting}

\arghead
\begin{itemize}[leftmargin=*]
  \item \code{A} is a \code{dpmat} object.
  \item \code{point} is a finite real scalar for a one-parameter object, such
        as \code{0.25}, or a finite real row vector with one entry per
        parameter, such as \code{[0.25 12]}.  Every entry must lie within the
        corresponding grid bounds.
  \item \code{val} is a numeric matrix with \code{size(A)}.  Coefficient-backed
        objects use local Bernstein interpolation; function-backed objects call
        their stored function handle.
\end{itemize}

For a degree-one scalar coefficient-backed object on \([\rho_0,\rho_1]\),
\[
  A(\rho) = a A_0 + (1-a)A_1,\qquad
  a = \frac{\rho_1-\rho}{\rho_1-\rho_0}.
\]
The same local-coordinate rule is applied entrywise for matrix-valued data.

\examplehead
Use the function-call form when the object is naturally one input among several
MATLAB expressions.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {2, 4}, Degree=1);
val = evaluate(A, 0.25)
\end{lstlisting}

\begin{lstlisting}[style=dpoutput]
val =
    2.5000
\end{lstlisting}

At \(\rho=0.25\), the local weight is \(a=0.75\), so the interpolated value is
\(0.75\cdot2+0.25\cdot4=2.5\).

The dot-call form is equivalent and can be convenient in command-window
exploration.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {2, 4}, Degree=1);
val = A.evaluate(0.75)
\end{lstlisting}

\begin{lstlisting}[style=dpoutput]
val =
    3.5000
\end{lstlisting}

Function-backed objects route through the retained function handle, so
non-polynomial expressions can still be evaluated exactly at a point.

\begin{lstlisting}[style=dpmatlab]
F = dpmat({[0 pi]}, @(rho) sin(rho));
val = F.evaluate(pi/2)
\end{lstlisting}

\begin{lstlisting}[style=dpoutput]
val =
     1
\end{lstlisting}

\subsection{Algebra Operators}
\label{sec:dpmat-algebra}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
C = A + B
C = A + M
C = M + A
C = A - B
C = A - M
C = M - A
C = +A
C = -A
C = A * B
C = A * M
C = M * A
\end{lstlisting}

\arghead
\begin{itemize}[leftmargin=*]
  \item Coefficient-backed \code{dpmat}: addition, subtraction, unary signs,
        and multiplication use local Bernstein coefficients.
  \item Numeric scalar, such as \code{5}, broadcasts to the \code{dpmat} matrix
        size when needed.
  \item Numeric matrix: accepted when the matrix size is compatible with the
        operation, such as \code{eye(2)} for a \(2\times2\) object.
  \item Mixed grids with same bounds: re-expressed on a common refinement.
  \item Mixed degrees: elevated to a common degree for coefficient-wise
        operations; multiplication produces the degree sum.
  \item Function-only \code{dpmat}: evaluates and plots, but does not enter
        coefficient algebra unless explicit \code{Degree} supplied coefficient
        evidence.
\end{itemize}

For addition and subtraction, the package elevates both operands to a common
degree before combining matching coefficients:
\[
  C_j = \widehat A_j + \widehat B_j.
\]
For multiplication, coefficient labels convolve and the output degree is the
sum of the input degrees.

\examplehead
Addition elevates the lower-degree operand before combining coefficients.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {1, 2}, Degree=1);
B = dpmat({[0 1]}, {10, 20, 30}, Degree=2);
S = A + B
cS = S.coeffs(1);
[cS{:}]
\end{lstlisting}

\begin{lstlisting}[style=dpoutput]

ans =
   11.0000   21.5000   32.0000
\end{lstlisting}

re-expressed on the union grid before their coefficients are combined.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {1, 2}, Degree=1);

\subsubsection{Operator-level entries}
\label{sec:dpmat-operator-entries}

\textbf{\code{plus}.} Adds two coefficient-backed objects or adds a compatible
numeric scalar/matrix.  The supported forms are
\code{C=A+B}, \code{C=A+M}, and \code{C=M+A}; grids are refined and degrees
are elevated before coefficient-wise addition.  For example,
\code{size(A+3)} returns the same matrix size as \code{A}.

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
C = A + B
C = A + M
C = M + A
\end{lstlisting}

\textbf{\code{minus}.} Subtracts compatible known-data objects or numeric
operands.  \code{A-M} and \code{M-A} preserve the left/right order of the
matrix subtraction.

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
C = A - B
C = A - M
C = M - A
\end{lstlisting}

\textbf{\code{uplus} and \code{uminus}.} Unary plus returns an equivalent
coefficient-backed object; unary minus negates every local coefficient.

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
B = +A
B = -A
\end{lstlisting}

\textbf{\code{mtimes}.} Performs a matrix product, scalar product, or numeric
matrix product.  The inner matrix dimensions must agree and the output degree
is the sum of operand degrees for two parameter-dependent operands.

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
C = A * B
C = A * M
C = M * A
\end{lstlisting}

\examplehead
For a two-parameter cell, multiplying two degree-one scalar value grids raises
\code{Degree} to 2 and produces \((2+1)^2=9\) tensor coefficients.

\begin{lstlisting}[style=dpmatlab]

A = dpmat(grid, {1 2; 3 4}, Degree=1);
B = dpmat(grid, {5 6; 7 8}, Degree=1);
K = A * B;
cK = K.coeffs([1 1]);
fprintf('Tensor product degree: %d\n', K.Degree);
fprintf('Tensor labels:\n');

fprintf('Tensor coefficients:\n');
disp([cK{:}])
\end{lstlisting}

\examplehead
Unary signs and numeric addition preserve the implemented \code{dpmat} type
and evaluation behavior.

\begin{lstlisting}[style=dpmatlab]

\subsection{Matrix Methods}
\label{sec:dpmat-matrix-ops}

Matrix methods act on every local Bernstein matrix coefficient; they do not
rearrange the scheduling grid.  Structural operations require coefficient
evidence.  A function-only \code{dpmat} can still use \code{evaluate},
\code{plot}, \code{uplus}, \code{squeeze}, shape inspection, and equality;
other structural operations reject it with \code{dpmat:FunctionOnlyAlgebra}.
The following families separate matrix shape from the Bernstein grid that
remains attached to the result.

\needspace{7\baselineskip}
\subsubsection{Shape Inspection And Identity}
\label{sec:dpmat-matrix-shape}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
sz = size(A)
sz = size(A, dim)
n = length(A)
n = height(A)
n = width(A)
n = numel(A)
n = ndims(A)
B = +A
tf = isequal(A, B, ...)
\end{lstlisting}

\arghead
\begin{itemize}[leftmargin=*]
  \item All shape queries report the two-dimensional matrix payload, never the
        physical-cell grid.  In particular, \code{ndims(A)} is \code{2}.
  \item Unary \code{+} returns an equivalent \code{dpmat}; it does not alter
        the stored coefficient evidence.
  \item \code{isequal} returns a logical scalar.  Coefficient-backed objects
        are compared after compatible grid refinement and degree elevation;
        function-only objects compare their stored metadata and handle.
\end{itemize}

\needspace{7\baselineskip}
\subsubsection{Transpose, Vectorization, Diagonals, And Reshape}
\label{sec:dpmat-matrix-transform}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
B = transpose(A)
B = ctranspose(A)
B = A.'
B = A'
B = vec(A)
B = diag(A)
B = diag(A, k)
B = reshape(A, [m n])
B = reshape(A, m, n)
B = squeeze(A)
\end{lstlisting}

For finite real payloads, \code{transpose} and \code{ctranspose} have the same
numerical effect.  \code{vec} uses MATLAB column-major vectorization.
\code{diag} extracts a diagonal, or constructs a square diagonal matrix from a
vector payload; its finite integer \code{k} may not select an empty diagonal.
\code{reshape} accepts exactly two positive dimensions, with at most one
inferred \code{[]} dimension, and preserves the matrix element count.
\code{squeeze} retains the package's two-dimensional matrix convention.

\examplehead
These structural methods return new \code{dpmat} objects whose matrix size
changes while the grid and degree metadata remain attached to the coefficient
storage.

\begin{lstlisting}[style=dpmatlab]

V = vec(A)
size(V)
D = diag(A)

size(R)
\end{lstlisting}

\needspace{7\baselineskip}
\subsubsection{Reordering And Repetition}
\label{sec:dpmat-matrix-reorder}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
B = flip(A)
B = flip(A, dim)
B = flipud(A)
B = fliplr(A)
B = rot90(A)
B = rot90(A, k)
B = repmat(A, m)
B = repmat(A, m, n)
B = repmat(A, [m n])
\end{lstlisting}

\code{flip} uses MATLAB's first nonsingleton matrix dimension by default;
\code{flipud} and \code{fliplr} select rows and columns.  \code{rot90}
defaults to one quarter-turn and accepts finite integer \code{k}.  \code{repmat}
accepts a positive scalar \code{m}, expanded to \code{[m m]}, two positive
integer repetition counts, or a two-element count vector.  These transformations
leave the physical grid and Bernstein degree unchanged.

\needspace{7\baselineskip}
\subsubsection{Block Assembly}
\label{sec:dpmat-matrix-assembly}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
C = horzcat(A, B, ...)
C = vertcat(A, B, ...)
C = [A, B]
C = [A; B]
C = cat(dim, A, B, ...)
C = blkdiag(A, B, ...)
\end{lstlisting}

The bracket forms call \code{horzcat} and \code{vertcat}; \code{cat} supports
only dimensions 1 and 2.  Every nonnumeric operand must be coefficient-backed,
and at least one operand of \code{cat} or \code{blkdiag} must be a
\code{dpmat}.  Finite real numeric blocks are promoted on the common grid.
Compatible grids with the same bounds are merged and lower-degree operands are
elevated before their coefficient payloads are assembled.

\examplehead
\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {1, 2}, Degree=1);
size([A, A])
size([A; A])
size(blkdiag(A, 5))
\end{lstlisting}

\subsection{Indexing And Assignment}
\label{sec:dpmat-indexing}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
B = A(rows, cols)
value = A.PropertyName
A(rows, cols) = numericValue
A(rows, cols) = B
\end{lstlisting}

\arghead
\begin{itemize}[leftmargin=*]
  \item \code{rows} and \code{cols} are ordinary MATLAB matrix subscripts,
        such as \code{:}, \code{end}, \code{1}, or \code{2:3}.
  \item \code{PropertyName} is a public property or method name for dot access.
  \item \code{numericValue} is a finite real matrix with the selected block
        size; \code{B} is a compatible coefficient-backed \code{dpmat} block.
  \item \code{value} is the property or method result.  \code{B} is a sliced
        \code{dpmat}; assignment updates every local coefficient and elevates
        degrees when required.
\end{itemize}

\examplehead
Indexing returns a smaller \code{dpmat}; assignment updates the corresponding
matrix entries in every local coefficient.

\begin{lstlisting}[style=dpmatlab]

topTail = A(1, 2:3)
A(:, 2) = 5;
A
\end{lstlisting}

\begin{lstlisting}[style=dpoutput]

  dpmat [2 1] over 1-D grid, degree 1, source coefficient-backed

topTail =
  dpmat [1 2] over 1-D grid, degree 1, source coefficient-backed

  dpmat [2 3] over 1-D grid, degree 1, source coefficient-backed
\end{lstlisting}

The assignment does not change the object degree because the numeric value is
promoted to degree-one coefficient data before insertion.

\subsection{Limits}
\label{sec:dpmat-limits}

\begin{itemize}[leftmargin=*]
  \item Function-only objects created without \code{Degree} do not have
        Bernstein coefficient evidence for \code{bernsteinTable} or coefficient algebra.
  \item Numeric operands must be finite real nonempty matrices with compatible
        sizes, or finite real scalars that can broadcast to the required size.
  \item Grid refinement is supported for matching parameter dimensions and
        matching grid bounds.
\end{itemize}

\section{\texorpdfstring{\code{dpvar}}{dpvar} Reference}
\label{sec:dpvar}

\code{dpvar} creates continuous cell-local Bernstein decision expressions backed
by YALMIP \code{sdpvar} coefficients.  It participates in supported affine and
known-data algebra.  It does not choose solvers or call \code{optimize};
solver-facing work happens after comparison overloads create \code{dplmi}
objects and \code{toYalmip} converts them to YALMIP constraints.

\subsection{Construction}
\label{sec:dpvar-construction}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
P = dpvar(n, gridVectors)
P = dpvar(n, n, gridVectors)
P = dpvar(n, m, gridVectors)
P = dpvar(..., "full")
P = dpvar(..., "symmetric")
P = dpvar(..., Degree=0)
P = dpvar(..., Degree=1)
P = dpvar(..., Degree=d)
P = dpvar(..., RateBounds=rb)
\end{lstlisting}

\arghead
\begin{itemize}[leftmargin=*]
  \item \code{dpvar(n, gridVectors)} creates an \(n\times n\) square variable
        using scalar-size shorthand; for example, \code{dpvar(2, {[0 1]})}.
        Square variables default to symmetric YALMIP coefficients.
  \item \code{dpvar(n, n, gridVectors)} is the explicit square-size form; for
        example, \code{dpvar(2, 2, {[0 1]})}.  It has the same default
        symmetric structure as the shorthand.
  \item \code{dpvar(n, m, gridVectors)} creates an \(n\times m\) variable.
        Rectangular variables default to full YALMIP coefficients; for example,
        \code{dpvar(2, 3, {[0 1]})}.
  \item \code{"full"} and \code{"symmetric"} explicitly choose the YALMIP
        coefficient structure.  \code{"symmetric"} requires a square size.
  \item \code{Degree=1} is the default continuous Bernstein decision variable.
        Every finite nonnegative integer \code{Degree=d} is supported.
        \code{Degree=0} creates one parameter-independent decision matrix
        shared across the grid; \code{d >= 1} creates continuous piecewise
        Bernstein data whose neighboring cells share complete control faces.
  \item \code{RateBounds=rb} stores parameter-rate metadata for later
        \code{rhodiff(P)} calls.  Use \code{RateBounds=[-1 1]} for one
        parameter; use a two-row matrix for two parameters, as shown in the
        rate-metadata example below.
\end{itemize}

\subsection{\texorpdfstring{\code{rhodiff}}{rhodiff}}
\label{sec:dpvar-rhodiff}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
D = rhodiff(P)
D = rhodiff(P, rb)
\end{lstlisting}

\arghead
\begin{itemize}[leftmargin=*]
  \item \code{P} is a \code{dpvar} without existing rate-vertex rows.
  \item \code{rb} is a finite \(\ell\)-by-\(2\) numeric matrix of lower and
        upper parameter-rate bounds, with each lower bound no greater than its
        upper bound.  It must equal \code{P.RateBounds} when the object already
        carries nonempty bounds.
  \item Without \code{rb}, \code{rhodiff(P)} requires nonempty
        \code{P.RateBounds}.
  \item \code{D} is a discontinuous \code{dpvar} with one coefficient row per
        rate vertex.  In one parameter a degree-\(m\) derivative has degree
        \(m-1\), while a degree-zero derivative remains zero; multivariate
        partials are elevated into the implementation's common tensor degree.
\end{itemize}

For a one-parameter degree-one coefficient pair \(P_0,P_1\) on a cell of width
\(h\), the rate-dependent derivative row is
\[
  \dot P(\rho,\dot\rho) = \dot\rho\,\frac{P_1-P_0}{h}.
\]
The implementation stores one row for each allowed rate vertex.

\examplehead
When rate bounds live on the object, \code{rhodiff(P)} uses them directly.

\begin{lstlisting}[style=dpmatlab]

D.RateBounds
\end{lstlisting}

\subsection{\texorpdfstring{\code{bernsteinTable}}{bernsteinTable}}
\label{sec:dpvar-table}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]

\end{lstlisting}

\arghead
\begin{itemize}[leftmargin=*]
  \item \code{P} is a \code{dpvar} object.

\arghead

\subsection{Matrix Methods}
\label{sec:dpvar-matrix-ops}

Matrix methods act on each local YALMIP-backed payload while preserving
compatible grid, degree, and rate metadata.  This is matrix structure, not
parameter-grid manipulation.  The families below use the same organization as
the \code{dpmat} reference, but their outputs remain \code{dpvar} expressions
and supported assembly may additionally use coefficient-backed \code{dpmat},
affine \code{sdpvar}, and numeric blocks.

\subsubsection{Shape Inspection And Identity}
\label{sec:dpvar-matrix-shape}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]

n = height(P)
n = width(P)

\arghead
\begin{itemize}[leftmargin=*]
  \item Shape queries report the two-dimensional matrix payload, never the
        physical-cell grid.  In particular, \code{ndims(P)} is \code{2}.
  \item Unary \code{+} preserves the decision expression and its coefficient
        graph.
  \item \code{isequal} returns a logical scalar only when the grid, degree,
        matrix size, metadata, and local YALMIP payloads are identical; it does
        not merge grids or elevate degrees.
\end{itemize}

\subsection{Indexing And Assignment}
\label{sec:dpvar-indexing}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
Q = P(rows, cols)
value = P.PropertyName
P(rows, cols) = numericValue
P(rows, cols) = Q
P(rows, cols) = A
P(rows, cols) = X
\end{lstlisting}

\arghead
\begin{itemize}[leftmargin=*]
  \item \code{rows} and \code{cols} are ordinary MATLAB matrix subscripts,
        such as \code{:}, \code{end}, \code{1}, or \code{1:2}.
  \item \code{PropertyName} is a public property or method name for dot access.
  \item \code{numericValue}, \code{Q}, \code{A}, and \code{X} are, respectively,
        a finite real matrix, compatible \code{dpvar}, coefficient-backed
        \code{dpmat}, or affine \code{sdpvar} block matching the selection.
  \item \code{value} is the property or method result.  \code{Q} is a sliced
        \code{dpvar}; assignment may elevate degrees and propagate compatible
        rate metadata across every physical cell and local coefficient.
\end{itemize}

\examplehead
Indexing returns a smaller \code{dpvar}; assignment updates the selected matrix
entries across every local coefficient.

\begin{lstlisting}[style=dpmatlab]
yalmip('clear')
P = dpvar(2, 3, {[0 1]}, "full");
col = P(:, 2);
P(:, 1) = 0;
class(col)
size(col)
size(P)
\end{lstlisting}

    'dpvar'

     2     1

\end{lstlisting}

\subsection{\texorpdfstring{\code{value}}{value}}
\label{sec:dpvar-value}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
A = value(P)
rows = value(rhodiff(P))
\end{lstlisting}

\code{value} converts assigned \code{dpvar} coefficients into known,
coefficient-backed \code{dpmat} data.  An ordinary expression returns one
\code{dpmat}, preserving its grid, matrix size, degree, local coefficient
order, and continuity metadata.  A rate-vertex expression created by
\code{rhodiff} returns a \(1\)-by-\(2^\ell\) cell array of \code{dpmat}
objects in \code{helper.combRows(RateBounds)} lower/upper vertex order.  The
returned \code{dpmat} objects do not carry rate metadata.  Every symbolic
coefficient must have an assigned finite real YALMIP value; otherwise the
method raises \code{dpvar:UnassignedValue}.

\examplehead
\begin{lstlisting}[style=dpmatlab]
yalmip('clear')
P = dpvar(1, [0 1], Degree=2);
c = P.coeffs(1);
assign([c{:}], [1 2 4]);
A = value(P);
A.coeffs(1)
\end{lstlisting}

\begin{lstlisting}[style=dpoutput]
ans =
    {[1]}    {[2]}    {[4]}
\end{lstlisting}

\subsection{Comparisons To \texorpdfstring{\code{dplmi}}{dplmi}}
\label{sec:dpvar-comparison}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
C = P <= 0

C = lhs <= rhs
C = lhs >= rhs
\end{lstlisting}

\arghead
\begin{itemize}[leftmargin=*]
  \item \code{P} and \code{lhs} are square, coefficient-wise symmetric or
        Hermitian \code{dpvar} expressions after residual assembly.
  \item \code{rhs} is commonly \code{0}; compatible numeric, \code{dpmat},
        affine \code{sdpvar}, and \code{dpvar} expressions are also accepted.
  \item \code{C} is a \code{dplmi} wrapper.  The comparison creates direct
        coefficient constraints but does not solve an optimization problem.
\end{itemize}

\examplehead
Comparison creates a \code{dplmi} wrapper with one stored constraint for each
physical cell and local Bernstein coefficient.

yalmip('clear')

\subsection{Limits}
\label{sec:dpvar-limits}

\begin{itemize}[leftmargin=*]
  \item Constructor-created \code{dpvar} objects support every finite
        nonnegative integer degree.  Higher degree increases the number of
        Bernstein control matrices per cell.
  \item Products may contain decision variables on at most one side; nonlinear
        decision products such as \code{P * Q} are outside this slice.
  \item Function-only \code{dpmat} operands cannot enter \code{dpvar} algebra
        unless they were constructed with explicit Bernstein evidence.
  \item \code{rhodiff} of an existing rate-vertex derivative expression is not
        part of the current public workflow.
\end{itemize}

\subsubsection{See Also}
\code{dpvar}, \code{rhodiff}, \code{bernsteinTable}, \code{dplmi},
\code{dpmat}.

\section{\texorpdfstring{\code{dplmi}}{dplmi} Reference}
\label{sec:dplmi}

\code{dplmi} stores direct coefficient-wise YALMIP constraints assembled from
square symmetric \code{dpvar} expressions.  It is the package boundary between
Bernstein coefficient objects and ordinary YALMIP solver calls.

\subsection{Construction And Comparisons}
\label{sec:dplmi-construction}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
C = dplmi(expr, relation)
C = dplmi(expr, relation, "UsePolya")
C = dplmi(expr, relation, UsePolya=true, PolyaDegree=d)
C = dplmi(expr, relation, "UsePolya", "PolyaDegree", d)
C = lhs <= rhs
C = lhs >= rhs
\end{lstlisting}

\arghead
\begin{itemize}[leftmargin=*]
  \item \code{expr} is a square \code{dpvar} expression whose coefficient
        matrices are symmetric or Hermitian; \code{relation} is exactly
        \code{"<="} or \code{">="}.
  \item \code{relaxLemma} is a logical reserved option with default
        \code{false}; \code{true} raises\linebreak[4]
        \code{dplmi:UnsupportedRelaxLemma}.
  \item \code{UsePolya} is a logical scalar option with default
        \code{false}. Its bare form, \code{"UsePolya"}, and
        \code{UsePolya=true} without a degree select increment one.
  \item \code{PolyaDegree=d} is a finite nonnegative integer scalar. It
        elevates the residual by \code{d} in every parameter direction before
        assembling constraints. Supplying it without \code{UsePolya} enables
        P\'olya and issues \codeerr{dplmi}{ImplicitUsePolya};
        \code{UsePolya=false} with positive \code{d} raises
        \codeerr{dplmi}{ConflictingPolyaOptions}.
  \item \code{C} is direct coefficient-wise assembly unless the opt-in
        P\'olya option is selected. Comparisons such as \code{lhs >= rhs} are
        the ordinary user-facing entry point and accept compatible numeric,
        \code{dpmat}, affine \code{sdpvar}, and \code{dpvar} right-hand sides.
\end{itemize}

\examplehead
The direct constructor is equivalent to the comparison path when the relation
and options are explicit.

\begin{lstlisting}[style=dpmatlab]
yalmip('clear')
P = dpvar(2, {[0 1]}, "symmetric");
C = dplmi(P, ">=", relaxLemma=false, UsePolya=false, PolyaDegree=0);

C.RelaxLemma
C.UsePolya
C.PolyaDegree
\end{lstlisting}

\subsection{Direct Coefficient Assembly}
\label{sec:dplmi-direct}

For each physical cell, local Bernstein coefficient, and rate-vertex row if
present, \code{dplmi} creates one YALMIP semidefinite constraint.  For an
ordinary expression with \(N_c\) physical cells and \(N_b\) Bernstein
coefficients per cell, the number of stored constraints is \(N_cN_b\).  For a
\code{rhodiff} expression with \(N_v\) rate vertices, the count becomes
\(N_cN_bN_v\).

\subsection{Opt-In P\'olya Assembly And \texorpdfstring{\code{applyPolya}}{applyPolya}}
\label{sec:dplmi-polya}

With \code{UsePolya=true}, \code{dplmi} first elevates the stored residual by
\code{PolyaDegree} in every parameter direction, then constrains every
elevated local coefficient and every active rate row. Thus, if the original
degree is \(m\), the count is
\(N_c (m+d+1)^\ell\) for ordinary expressions and
\(N_c (m+d+1)^\ell N_v\) for rate-vertex expressions. An increment of zero is
valid and has the same coefficient count as direct assembly.

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
Cpolya = C.applyPolya()
Cpolya = C.applyPolya(d)
\end{lstlisting}

\code{applyPolya} is a value-class method: it returns a new \code{dplmi},
leaves \code{C} unchanged, and rebuilds from \code{C.Residual}. Selecting a
new increment therefore replaces rather than compounds a previous selection.
The no-argument form uses one; an invalid increment raises
\code{dplmi:InvalidPolyaDegree}.

\examplehead
\begin{lstlisting}[style=dpmatlab]
yalmip('clear')
P = dpvar(1, {[0 1]}, Degree=1);
direct = P >= 0;
polya = direct.applyPolya(2);
direct.PolyaDegree
polya.UsePolya
polya.PolyaDegree
numel(polya.Constraints)
\end{lstlisting}

\begin{lstlisting}[style=dpoutput]
ans =
     0

ans =
  logical
   1

ans =
     2

ans =
     4
\end{lstlisting}

\subsection{\texorpdfstring{\code{toYalmip}}{toYalmip}}
\label{sec:dplmi-toyalmip}

\syntaxhead
\begin{lstlisting}[style=dpsyntax]
F = toYalmip(C)

\arghead
\code{toYalmip} concatenates the stored constraint cells into a YALMIP

\subsection{Solver-Facing Use}
\label{sec:dplmi-solver-use}

\code{dplmi} does not own solver settings or wrap \code{optimize}.  After
\code{toYalmip}, use ordinary YALMIP:

\begin{lstlisting}[style=dpsyntax]
opts = sdpsettings("solver", solverName, "verbose", 0);
sol = optimize([C1.toYalmip, C2.toYalmip], objective, opts);
\end{lstlisting}

The solver selected by YALMIP must be available on the MATLAB path.  The current
test suite prefers MOSEK when available and otherwise falls back to LMILAB for
smoke coverage.

\section{Examples}
\label{sec:examples}

\subsection{Parameter-Dependent Lyapunov Solver Smoke}
\label{sec:parameter-dependent-lyapunov-smoke}

The first solver smoke test in \code{+tests/+dplmi/test_solver_smoke.m}
contrasts a constant Lyapunov matrix with a degree-one, parameter-dependent
one.  It solves the same decay and positivity constraints in both cases.  The
degree-one solution is then materialized as known \code{dpmat} data and
plotted.  \code{dpvar} is a decision-expression class and does not itself
provide \code{plot}; applying \code{value} to its local YALMIP payloads after
a successful solve supplies the numeric Bernstein coefficients for
\code{dpmat}.

\begin{lstlisting}[style=dpmatlab]
yalmip('clear')
grid = {[0 1]};
A = dpmat(grid, @(x) (1 - x) * [-1 -1; 1 -1] + ...
    x * [-1 -10; 0.1 -1], Degree=1);
solver = 'lmilab';
if exist('mosekopt', 'file') ~= 0
    solver = 'mosek';
end
opts = sdpsettings('solver', solver, 'verbose', 0);

Pc = dpvar(2, grid, Degree=0);
CconstantDecay = Pc * A + A' * Pc <= -1e-10 * eye(2);
CconstantPositive = Pc >= eye(2);
solConstant = optimize([CconstantDecay.toYalmip, ...
    CconstantPositive.toYalmip], [], opts);

Pd = dpvar(2, grid);
CdependentDecay = Pd * A + A' * Pd <= -1e-10 * eye(2);
CdependentPositive = Pd >= eye(2);
solDependent = optimize([CdependentDecay.toYalmip, ...
    CdependentPositive.toYalmip], [], opts);
assert(solDependent.problem == 0, solDependent.info)

Pplot = dpmat(grid, ...
    {cellfun(@value, Pd.LocalValues{1}, UniformOutput=false)}, ...
    Degree=Pd.Degree);
figure(Name="Parameter-dependent Lyapunov matrix")
plot(Pplot, SamplesPerCell=40, LineWidth=1.5)
title("Solved parameter-dependent Lyapunov matrix")
\end{lstlisting}

The figure contains one curve for each entry of the solved \(2\)-by-\(2\)
matrix \(P(\rho)\), sampled on the parameter interval.  It is a diagnostic
visualization of the feasible solution, not a certificate beyond the
coefficient-wise constraints supplied to the solver.  The constant-case result
is retained to exercise the comparison in the smoke test; only a MOSEK solve
is used there to certify its intended infeasibility distinction.

\subsection{Rate-Dependent Block LMI Solver Smoke}
\label{sec:solver-example}

This example is adapted from \code{+tests/+dplmi/test_solver_smoke.m}.  The
goal is to find a parameter-dependent \(P(\rho)\) and scalar \(\gamma\) such
that, on every Bernstein coefficient and rate vertex,
\[
\begin{bmatrix}
\dot P + PA + A^\top P & PB & C^\top\\
B^\top P & -\gamma I & D^\top\\
C & D & -\gamma I
\end{bmatrix}
\preceq 0,
\qquad
P(\rho)\succeq 0.
\]
The derivative term \(\dot P\) is built with \code{rhodiff(P, [-1 1])}.  The
comparison operators create \code{dplmi} wrappers, and \code{toYalmip} hands
the coefficient-wise constraints to YALMIP.

\begin{lstlisting}[style=dpmatlab]
yalmip('clear')
grid = linspace(0, 1, 2);
A = dpmat(grid, @(x) [-1, 0.5; -1, -2] + ...
    x * [-1.3, -20; 2, -10], Degree=1);
B = dpmat(grid, @(x) [1, -4; -1, -1] + ...
    x * [2.2, 0.5; -6, -5], Degree=1);
Cmat = eye(2);
Dmat = zeros(2);

P = dpvar(2, grid);
diffP = rhodiff(P, [-1 1]);
gamma = dpvar(1, grid, Degree=0);
E1 = [diffP + P * A + A' * P, P * B, Cmat';
      B' * P, -gamma * eye(2), Dmat';
      Cmat, Dmat, -gamma * eye(2)] <= 0;
E2 = P >= 0;
\end{lstlisting}

\begin{lstlisting}[
  style=dpmatlab,
  title={\textcolor{dpblue}{\sffamily\bfseries\footnotesize MATLAB input (continued)}}
]
objective = gamma.LocalValues{1}{1};
solver = 'lmilab';
if exist('mosekopt', 'file') ~= 0
    solver = 'mosek';
end
opts = sdpsettings('solver', solver, 'verbose', 0);
sol = optimize([E1.toYalmip, E2.toYalmip], objective, opts);
assert(sol.problem == 0, sol.info)
gammaValue = value(objective);
assert(isfinite(gammaValue))
fprintf("Optimal H-infinity gamma: %.6g\n", gammaValue)

numel(E1.Constraints)
numel(E2.Constraints)
\end{lstlisting}

The \code{fprintf} call prints the actual numeric \(\gamma\), whose value is
solver- and tolerance-dependent; the final two commands report six and two
constraints.

\section{Current Limits}
\label{sec:current-limits}

\begin{itemize}[leftmargin=*]
  \item \code{dplmi} assembles direct coefficient-wise constraints by default
        and supports opt-in cell-local P\'olya degree elevation. The
        relaxation-lemma workflow remains reserved and unsupported.
  \item Package-owned solver wrappers, strictness-margin diagnostics, residual
        evidence, and advanced relaxation workflows are not part of the current
        public API.
  \item \code{dpvar} is an affine YALMIP/Bernstein expression object.  It does
        not support nonlinear decision products.
  \item \code{dpmat} function-only objects evaluate exactly, but coefficient
        algebra requires Bernstein coefficient evidence.
  \item \code{dpbase} is documented for architecture and advanced inspection.
        Primary modeling workflows should use \code{dpmat}, \code{dpvar}, and
        \code{dplmi}.
\end{itemize}
