\begin{abstract}
This manual describes the current public behavior of the \pkg.  The present
implementation provides \code{dpbase} for cell-local Bernstein coefficient
storage, \code{dpmat} for known finite real matrix data on tensor grids, and
an initial \code{dpvar} layer for continuous degree-1 YALMIP-backed decision
expressions.  Solver-facing \code{dplmi} assembly, SDP solver invocation, and
relaxation-lemma workflows remain future package layers in this repository
version.
\end{abstract}

\section{Installation And Verification}

\subsection{Add The Package To The MATLAB Path}

Start \matlab{} in the repository root, or set \code{projectRoot} to the
absolute path of the checked-out repository.  Add the package recursively, then
remove the documentation directory from the executable path.

\begin{lstlisting}[style=dpmatlab]
projectRoot = "path/to/Differential Parameter-Dependent Linear Matrix Inequality";
addpath(genpath(projectRoot));
rmpath(genpath(fullfile(projectRoot, "doc")));
\end{lstlisting}

For local development from the repository root, the shorter form is enough:

\begin{lstlisting}[style=dpmatlab]
addpath(pwd)
\end{lstlisting}

\subsection{Run The Current Test Suite}

The current verification entry point runs the non-SDP tests for
\code{+helper}, \code{@dpbase}, \code{@dpmat}, and \code{@dpvar}.  The
\code{@dpvar} tests require YALMIP to be available on the \matlab{} path.

\begin{lstlisting}[style=dpmatlab]
results = tests.run_all;
table(results)
\end{lstlisting}

Expected result: all currently implemented tests pass.  The suite covers helper
validation, \code{dpbase} construction, grid metadata, local storage, label
ordering, rate-bound validation, and current \code{dpmat} construction,
evaluation, algebra, display, plotting, matrix operations, indexing,
assignment, structural transforms, and error boundaries.  It also covers the
current \code{dpvar} constructor, continuity-by-shared-coefficients behavior,
affine algebra, mixed known/decision products, matrix operations, indexing,
assignment, and validation boundaries.

The command above does not verify \code{dplmi} assembly, SDP solver calls,
relaxation lemma assembly, or DP-LMI feasibility workflows because those public
layers are not implemented in this version.

\section{Quick Start}

\code{dpbase} stores one flat Bernstein coefficient cell for each physical cell
of a tensor grid.  \code{dpmat} builds on that storage to represent known
parameter-dependent matrices.

\subsection{A Scalar Grid}

\begin{lstlisting}[style=dpmatlab]
obj = dpbase({[0 1 3]}, [2 3], 1);

obj.MatrixSize
obj.Degree
obj.GridInfo.Bounds
obj.npar()
obj.ncell()
obj.ncoeff()
size(obj)
obj.cells()
obj.lbls()
\end{lstlisting}

Expected structural outputs:

\begin{lstlisting}[style=dpoutput]
MatrixSize =
     2     3

Degree =
     1

Bounds =
     0     3

npar()   -> 1
ncell()  -> 2
ncoeff() -> 2
size(obj)-> [2 3]

cells() =
     1
     2

lbls() =
     0
     1
\end{lstlisting}

There are two physical intervals, \([0,1]\) and \([1,3]\).  Because the degree
is one and the grid is one-dimensional, each physical cell stores two local
Bernstein coefficients.

\subsection{Access Local Coefficients}

\begin{lstlisting}[style=dpmatlab]
c1 = obj.coeffs(1);
c2 = obj.coeffs(2);
\end{lstlisting}

Expected result: both \code{c1} and \code{c2} are \code{1x2} cell arrays.  Each
entry is a numeric zero matrix of size \code{2x3}.  The first cell corresponds
to local labels \(0\) and \(1\) on the interval \([0,1]\); the second cell uses
the same local labels on the interval \([1,3]\).

\subsection{A Tensor Grid}

\begin{lstlisting}[style=dpmatlab]
obj = dpbase({[0 1 2], [10 20 30]}, [1 1], 1);

obj.GridInfo.Points
obj.cells()
obj.lbls()
obj.coeffs([2 1])
\end{lstlisting}

Expected structural outputs:

\begin{lstlisting}[style=dpoutput]
GridInfo.Points =
     0    10
     0    20
     0    30
     1    10
     1    20
     1    30
     2    10
     2    20
     2    30

cells() =
     1     1
     1     2
     2     1
     2     2

lbls() =
     0     0
     0     1
     1     0
     1     1
\end{lstlisting}

The first parameter index varies more slowly than the second.  This row order
is used consistently for physical cells and local Bernstein labels.

\subsection{A Known Matrix}

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {2, 4}, Degree=1);

A.MatrixSize
A.Degree
A.SourceSummary
A.evaluate(0.25)
C = A + 5;
C.coeffs(1)
\end{lstlisting}

Expected structural outputs:

\begin{lstlisting}[style=dpoutput]
MatrixSize =
     1     1

Degree =
     1

SourceSummary =
    "coefficient-backed"

A.evaluate(0.25) -> 2.5
C.coeffs(1)      -> {7, 9}
\end{lstlisting}

The expression \code{A + 5} returns another coefficient-backed \code{dpmat} on
the same grid.

\subsection{A Function-Backed Known Matrix}

\begin{lstlisting}[style=dpmatlab]
F = dpmat({[0 pi]}, @(rho) sin(rho));

F.SourceSummary
F.evaluate(pi/2)
F.coeffs(1)
\end{lstlisting}

Expected outputs:

\begin{lstlisting}[style=dpoutput]
SourceSummary =
    "function"

F.evaluate(pi/2) -> 1
F.coeffs(1)      -> {0, 0}
\end{lstlisting}

Function-backed \code{dpmat} objects without an explicit \code{Degree} keep the
exact function handle for evaluation.  The inherited local coefficients are
placeholder zeros used only to satisfy shared \code{dpbase} storage; they are
not Bernstein evidence and cannot enter coefficient algebra.

\subsection{A Continuous Decision Variable}

\begin{lstlisting}[style=dpmatlab]
P = dpvar(2, {[0 1 2]}, "symmetric");

P.MatrixSize
P.Degree
P.IsContinuous
P.ContainsDecision
left = P.coeffs(1);
right = P.coeffs(2);
isequal(getvariables(left{2}), getvariables(right{1}))
\end{lstlisting}

Expected structural outputs:

\begin{lstlisting}[style=dpoutput]
MatrixSize =
     2     2

Degree =
     1

IsContinuous    -> true
ContainsDecision-> true
shared boundary -> true
\end{lstlisting}

\code{dpvar} creates YALMIP decision coefficients on the global grid nodes and
reuses the same coefficient handles in adjacent physical cells.  Continuity is
therefore built into storage; no equality LMI is added by the constructor.

\section{Bernstein And Grid Background}

\subsection{One Cell, Local Coordinates}

On one physical interval \([\rho_0,\rho_1]\), the package uses the normalized
coordinate
\[
  \alpha = \frac{\rho_1-\rho}{\rho_1-\rho_0},
  \qquad 0 \leq \alpha \leq 1.
\]
A degree-\(m\) Bernstein polynomial is written as
\[
  P(\alpha) = \sum_{i=0}^{m} C_i B_i^m(\alpha),
  \qquad
  B_i^m(\alpha) = \binom{m}{i}\alpha^{m-i}(1-\alpha)^i.
\]
For matrix-valued data, each coefficient \(C_i\) is a matrix with the same
payload size.  \code{dpbase} stores those matrices as one flat coefficient
cell for each physical grid cell.

\begin{center}
\begin{tikzpicture}[x=4.2cm,y=2.1cm,>=Latex]
  \draw[->] (-0.05,0) -- (1.12,0) node[right] {$\rho$};
  \draw[thick] (0,0) -- (1,0);
  \draw[fill=black] (0,0) circle (1.3pt) node[below] {$\rho_0$};
  \draw[fill=black] (1,0) circle (1.3pt) node[below] {$\rho_1$};
  \draw[blue!65!black,thick] (0,0.35) -- (1,0.95);
  \node[blue!65!black,above] at (0,0.35) {$C_0$};
  \node[blue!65!black,above] at (1,0.95) {$C_1$};
  \node at (0.5,-0.38) {one physical cell, two degree-1 local labels};
\end{tikzpicture}
\end{center}

Degree one is the line-segment case.  It is useful intuition for
piecewise-linear \code{dpmat} data and for the current degree-1 \code{dpvar}
constructor, but Bernstein storage is not limited to splines.

\subsection{Quadratic And Higher-Degree Bases}

For degree two, one cell has three local labels \(0,1,2\):
\[
  P(\alpha) =
  C_0\alpha^2 + 2C_1\alpha(1-\alpha) + C_2(1-\alpha)^2.
\]
The middle coefficient \(C_1\) controls the interior Bernstein basis function,
not an extra physical grid node.  The physical interval still has two endpoints;
the polynomial degree controls how many local coefficient labels live inside
that cell.

\begin{center}
\begin{tikzpicture}[x=6.0cm,y=2.8cm,>=Latex]
  \draw[->] (-0.04,0) -- (1.08,0) node[right] {$\alpha$};
  \draw[->] (0,-0.04) -- (0,1.12) node[above] {$B_i^2$};
  \draw[gray!35] (0,0) grid[xstep=0.25,ystep=0.25] (1,1);
  \draw[blue!70!black,thick,domain=0:1,samples=80]
    plot (\x,{(\x)^2});
  \draw[green!45!black,thick,domain=0:1,samples=80]
    plot (\x,{2*(\x)*(1-\x)});
  \draw[red!70!black,thick,domain=0:1,samples=80]
    plot (\x,{(1-\x)^2});
  \node[blue!70!black] at (0.82,0.78) {$B_0^2$};
  \node[green!45!black] at (0.50,0.62) {$B_1^2$};
  \node[red!70!black] at (0.18,0.78) {$B_2^2$};
  \node[below] at (0,0) {$0$};
  \node[below] at (1,0) {$1$};
\end{tikzpicture}
\end{center}

The same pattern extends to any degree \(m\).  A cubic cell stores four
coefficient labels \(0,1,2,3\), a quartic cell stores five, and so on.  The
labels are local to the current physical cell; adjacent cells have their own
local coefficient cells even when continuous objects share boundary handles.

\subsection{Products And Degree Growth}

Multiplication is the main reason the package treats Bernstein labels as
coefficient data rather than as samples.  On one cell, multiplying two
degree-1 factors produces a degree-2 polynomial:
\[
\begin{aligned}
  P(\alpha) &= \alpha P_0 + (1-\alpha)P_1,\\
  Q(\alpha) &= \alpha Q_0 + (1-\alpha)Q_1,\\
  P(\alpha)Q(\alpha)
    &= B_0^2 P_0Q_0
     + B_1^2 \frac{P_0Q_1 + P_1Q_0}{2}
     + B_2^2 P_1Q_1.
\end{aligned}
\]

\begin{center}
\begin{tikzpicture}[x=6.2cm,y=2.4cm,>=Latex]
  \draw[->] (-0.04,0) -- (1.08,0) node[right] {$\alpha$};
  \draw[->] (0,-0.08) -- (0,1.22) node[above] {value};
  \draw[gray!30] (0,0) grid[xstep=0.25,ystep=0.25] (1,1);
  \draw[blue!65!black,thick] (0,0.25) -- (1,0.95);
  \draw[orange!85!black,thick] (0,0.90) -- (1,0.35);
  \draw[purple!70!black,very thick,domain=0:1,samples=80]
    plot (\x,{(0.25 + 0.70*\x)*(0.90 - 0.55*\x)});
  \node[blue!65!black] at (0.84,1.05) {$P$};
  \node[orange!85!black] at (0.17,1.02) {$Q$};
  \node[purple!70!black] at (0.64,0.42) {$PQ$};
  \node[below] at (0,0) {$0$};
  \node[below] at (1,0) {$1$};
\end{tikzpicture}
\end{center}

For general scalar degrees \(n\) and \(m\),
\[
  P(\alpha) = \sum_i P_i B_i^n(\alpha),
  \qquad
  Q(\alpha) = \sum_j Q_j B_j^m(\alpha),
\]
and
\[
  P(\alpha)Q(\alpha) =
  \sum_{k=0}^{n+m} R_k B_k^{n+m}(\alpha),
\]
where
\[
  R_k =
  \sum_{i+j=k} P_iQ_j
  \frac{\binom{n}{i}\binom{m}{j}}{\binom{n+m}{k}}.
\]
For example, if \(P\) has degree two and \(Q\) has degree three, then the
degree-five coefficient with label \(k=2\) is
\[
  R_2 =
  \frac{3}{10}P_0Q_2
  + \frac{6}{10}P_1Q_1
  + \frac{1}{10}P_2Q_0.
\]
This is the binomial-normalized convolution used by coefficient-backed
\code{dpmat} multiplication and by mixed known/decision products that remain
affine in YALMIP variables.

\subsection{Tensor-Product Labels}

For \(\ell\) parameter dimensions and scalar degree \(m\), each local label is
an \(\ell\)-tuple in \(\{0,\ldots,m\}^{\ell}\).  The number of local
coefficients per physical cell is
\[
  (m+1)^\ell.
\]
For example, \(\ell=2\) and \(m=1\) gives labels
\[
  (0,0),\ (0,1),\ (1,0),\ (1,1),
\]
which is exactly the order returned by \code{obj.lbls()}.

\begin{center}

Tensor-product multiplication adds labels component-wise.  In two dimensions,
a label \((i_1,i_2)\) from degree \(n\) and a label \((j_1,j_2)\) from degree
\(m\) contribute to result label
\[
  (k_1,k_2) = (i_1+j_1,\ i_2+j_2),
\]
with a scale factor that is the product of the one-dimensional binomial ratios.
For three parameters, the same rule applies to triples such as
\((i_1,i_2,i_3)+(j_1,j_2,j_3)\).  This is why a degree-1 object over a
three-dimensional parameter grid has \(2^3=8\) local coefficient labels per
physical cell.

\subsection{Data Layout Seen From MATLAB}

The physical grid and the local Bernstein labels are separate.  A two-parameter
\code{dpmat} with a degree-1 global coefficient grid stores four local
coefficients per physical cell:

A.evaluate([0.25, 12.5])
\end{lstlisting}

\section{\texorpdfstring{\code{dpbase}}{dpbase} Reference}

\subsection{Purpose}

\code{dpbase} is the shared coefficient-backed storage class for gridded
DP-LMI objects.  It stores tensor-grid metadata, matrix payload size, Bernstein
degree, nested physical-cell coefficient data, and rate-dependence metadata.

\subsection{Syntax}

\begin{lstlisting}[style=dpmatlab]
obj = dpbase(gridVectors, matrixSize, degree)
obj = dpbase(gridVectors, matrixSize, degree, localValues)
obj = dpbase(gridVectors, matrixSize, degree, localValues, Name=Value)
\end{lstlisting}

\subsection{Inputs}

\begin{tabularx}{\linewidth}{@{}>{\raggedright\arraybackslash}p{0.25\linewidth}>{\raggedright\arraybackslash}X@{}}
\toprule
Input & Description \\
\midrule
\code{gridVectors} &
Nonempty cell array of grid node vectors.  Each vector must be finite, real,
strictly increasing, numeric, and contain at least two nodes. \\
\code{matrixSize} &
\code{1x2} positive integer vector giving the row and column size of every
coefficient payload. \\
\code{degree} &
Nonnegative integer scalar Bernstein degree. \\
\code{localValues} &
Optional nested cell payload.  If omitted or empty, \code{dpbase} creates zero

\bottomrule
\end{tabularx}

\subsection{Name-Value Options}

\begin{tabularx}{\linewidth}{@{}>{\raggedright\arraybackslash}p{0.3\linewidth}>{\raggedright\arraybackslash}X@{}}

\midrule

\subsection{Custom Local Values}

For a one-dimensional grid with two physical cells and degree two, each physical
cell must store three local coefficients.

\begin{lstlisting}[style=dpmatlab]
localValues = {{11, 12, 13}, {21, 22, 23}};
obj = dpbase({[0 1 2]}, [1 1], 2, localValues);

obj.coeffs(2)
obj.coeffs({1})
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
obj.coeffs(2)  -> {21, 22, 23}
obj.coeffs({1})-> {11, 12, 13}
\end{lstlisting}

For a tensor grid, physical cells are nested one parameter dimension at a time.
The storage contract is \code{LocalValues\{i1\}\{i2\}...}, not
\code{LocalValues\{i1,i2,...\}}.

\begin{lstlisting}[style=dpmatlab]
mkCoeff = @(offset) {offset+1, offset+2, offset+3, offset+4};
localValues = {
    {mkCoeff(110), mkCoeff(120)}, ...
    {mkCoeff(210), mkCoeff(220)}
    };

obj = dpbase({[0 1 2], [10 20 30]}, [1 1], 1, localValues);
obj.coeffs([2 1])
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
ans =
  1x4 cell array
    {[211]}    {[212]}    {[213]}    {[214]}
\end{lstlisting}

\subsection{Rate Metadata}

\code{dpbase} validates rate bounds and rate-affine coefficient payloads, but it
does not enumerate rate vertices or assemble LMIs.  That solver-facing work is
reserved for a future \code{dplmi} layer.

\begin{lstlisting}[style=dpmatlab]
obj = dpbase({[0 1], [10 20]}, [1 1], 0, [], ...
    RateBounds=[-1 1; -2 2]);

obj.HasRateDependence
obj.RateBounds
obj.coeffs([1 1])
\end{lstlisting}

Expected result: \code{HasRateDependence} is true, \code{RateBounds} is the
given \code{2x2} table, and the single local coefficient remains the numeric
zero payload.

Rate-affine payloads use a scalar struct with fields \code{Constant} and
\code{Rate}.  The \code{Rate} field must be a cell array with one matrix per
parameter dimension.

\begin{lstlisting}[style=dpmatlab]
payload = struct("Constant", eye(2), "Rate", {{ones(2), 2*ones(2)}});
localValues = {{{payload}}};
obj = dpbase({[0 1], [10 20]}, [2 2], 0, localValues, ...
    RateBounds=[-1 1; -2 2]);
\end{lstlisting}

The stored coefficient represents the compact form
\[
  C(\dot\rho) =
  C_0 + C_1\dot\rho_1 + C_2\dot\rho_2,
\]
but \code{dpbase} only stores and validates this payload.  It does not solve or
test any inequality involving \(\dot\rho\).

\subsection{Validation And Error Boundaries}

The constructor rejects malformed inputs early and uses domain-specific error
identifiers.  The following examples are expected to error:

\begin{lstlisting}[style=dpmatlab]
dpbase([0 1], [1 1], 0)                 % dpbase:InvalidGrid
dpbase({[0 1 1]}, [1 1], 0)             % dpbase:InvalidGridVector
dpbase({[0 1]}, [1 0], 0)               % dpbase:InvalidMatrixSize
dpbase({[0 1]}, [1 1], -1)              % dpbase:InvalidDegree
dpbase({[0 1]}, [1 1], 0, [], ...
    HasRateDependence=true)             % dpbase:InvalidRateBounds
\end{lstlisting}

Plain coefficient payloads at the \code{dpbase} layer must be finite, real,
numeric matrices matching \code{matrixSize}.  Symbolic YALMIP payloads are not
accepted by \code{dpbase}; they belong in future subclasses that can define
symbolic algebra and solver assembly coherently.

\section{\texorpdfstring{\code{dpmat}}{dpmat} Reference}

\subsection{Purpose}

\code{dpmat} represents known finite real matrix data on a parameter grid.  It
inherits \code{dpbase} storage and adds source handling, exact function
evaluation, coefficient-backed algebra, matrix structural operations, and
two-dimensional block indexing for known data.

\subsection{Syntax}

\begin{lstlisting}[style=dpmatlab]
A = dpmat(gridVectors, source)
A = dpmat(gridVectors, source, Degree=m)
val = A.evaluate(point)
val = evaluate(A, point)
C = A + B
C = A - B
C = -A
C = +A
C = A * B
C = A * M
C = M * A
T = A.'
H = A'
C = [A, B]
C = [A; B]
C = cat(1, A, B)
C = cat(2, A, B)
B = A(rows, cols)
A(rows, cols) = rhs
d = length(A)
d = height(A)
d = width(A)
d = numel(A)
d = ndims(A)
B = squeeze(A)
tf = isequal(A, B)
d = diag(A)
B = diag(A, k)
B = reshape(A, m, n)
B = reshape(A, [], n)
v = vec(A)
L = tril(A)
L = tril(A, k)
U = triu(A)
U = triu(A, k)
B = blkdiag(A, M)
disp(A)
display(A)
h = plot(A)
h = plot(A, dims, SamplesPerCell=n, Name, Value)
\end{lstlisting}

\code{source} can be a function handle, a global cell grid of numeric Bernstein
coefficients, or explicit nested \code{LocalValues} in the \code{dpbase}
contract.

\subsection{Source Modes}

\begin{tabularx}{\linewidth}{@{}>{\raggedright\arraybackslash}p{0.28\linewidth}>{\raggedright\arraybackslash}X@{}}
\toprule
Mode & Behavior \\
\midrule
Function handle, no \code{Degree} &
Stores the exact \code{FunctionHandle}, probes the lower grid point only to
infer matrix size, sets \code{Degree=1}, and leaves inherited coefficients as
placeholder zeros.  Function-only objects use
\code{SourceSummary="function"} and cannot enter coefficient algebra. \\
Function handle with \code{Degree} &
Validates that the handle is representable as local Bernstein data of that
degree, populates \code{LocalValues}, keeps the exact \code{FunctionHandle}, and
uses \code{SourceSummary="function-bernstein"}. \\
Global cell grid &
Converts overlapping global Bernstein coefficient grids into flat local
coefficient cells.  The public helper \code{helper.cell2bern} exposes this same
conversion for inspection.  For degree \(m\), the global cell array size must
be \((n_{\mathrm{cell}}m)+1\) along each parameter dimension. \\
Nested \code{LocalValues} &
Passes explicit local coefficients through the \code{dpbase} nested-cell
contract.  The degree is inferred from the flat coefficient count
\((m+1)^{\ell}\) when it is not supplied explicitly. \\
\bottomrule
\end{tabularx}

All current \code{dpmat} objects are continuous known data.  Their fixed
metadata is:
\begin{itemize}[leftmargin=*]
  \item \code{IsContinuous=true}
  \item \code{ContainsDecision=false}
  \item \code{HasRateDependence=false}
\end{itemize}
Constructor options that try to override those metadata fields are rejected.

\subsection{Evaluation}

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {2, 4}, Degree=1);
A.evaluate(0.75)

B = dpmat({[0 1], [10 20]}, {1, 3; 5, 7}, Degree=1);
B.evaluate([0.25, 12.5])

F = dpmat({[0 pi]}, @(rho) sin(rho));
F.evaluate(pi/2)
\end{lstlisting}

Expected outputs:

\begin{lstlisting}[style=dpoutput]
A.evaluate(0.75)        -> 3.5
B.evaluate([0.25 12.5]) -> 2.5
F.evaluate(pi/2)        -> 1
\end{lstlisting}

Coefficient-backed objects evaluate by Bernstein interpolation on the active
physical cell.  Function-backed objects evaluate through the retained exact
handle.  Evaluation points must be finite, real, have one entry per parameter
dimension, and lie inside the grid bounds.

\subsection{Coefficient Algebra}

\code{dpmat} supports coefficient-backed \code{+}, \code{-}, unary \code{-}, and
matrix \code{*}.  Numeric scalars and compatible numeric matrices promote to
constant \code{dpmat} operands.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {1, 2}, Degree=1);
B = dpmat({[0 1]}, {10, 20, 30}, Degree=2);
C = A + B;

C.Degree
C.coeffs(1)
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
C.Degree   -> 2
C.coeffs(1)-> {11, 21.5, 32}
\end{lstlisting}

Multiplication raises Bernstein degree through binomial-normalized local
coefficient convolution.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {[1 2], [3 4]}, Degree=1);
B = dpmat({[0 1]}, {[5; 6], [7; 8]}, Degree=1);
K = A * B;

K.Degree
size(K)
K.coeffs(1)
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
K.Degree   -> 2
size(K)    -> [1 1]
K.coeffs(1)-> {17, 31, 53}
\end{lstlisting}

Same-bound mixed scalar grids are aligned on a common refinement before
coefficient algebra.  Mixed physical bounds are rejected.  Function-only
\code{dpmat} objects are rejected by coefficient algebra until exact
function-handle algebra is designed.

\subsection{Matrix Operations And Indexing}

\code{dpmat} supports transpose, conjugate transpose for real data, horizontal
and vertical concatenation, \code{cat} along dimensions 1 and 2, two-dimensional
matrix slicing, block assignment, matrix-payload shape inspection, and common
structural transforms.  Row and column subscripts support \code{:}, positive
integer vectors, full-length logical vectors, and \code{end}.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {
    [1 2 3; 4 5 6], ...
    [10 20 30; 40 50 60]
    }, Degree=1);

lastCol = A(:, end);
firstRow = A([true false], :);

size(lastCol)
lastCol.coeffs(1)
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
size(lastCol)     -> [2 1]
lastCol.coeffs(1)-> {[3; 6], [30; 60]}
\end{lstlisting}

Assignment accepts numeric constants and compatible \code{dpmat} blocks.  It
does not support deletion assignment, matrix growth, unsupported dimensions, or
coefficient operations on function-only objects.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {zeros(2), 2*ones(2)}, Degree=1);
A(:, 2) = 5;
A.coeffs(1)
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
A.coeffs(1)-> {[0 5; 0 5], [2 5; 2 5]}
\end{lstlisting}

\subsection{Shape And Structural Methods}

Shape methods report the size of each matrix payload, not the number of
physical cells or coefficients.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {zeros(2, 3), ones(2, 3)}, Degree=1);

length(A)
height(A)
width(A)
numel(A)
ndims(A)
squeeze(A)
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
length(A) -> 3
height(A) -> 2
width(A)  -> 3
numel(A)  -> 6
ndims(A)  -> 2
squeeze(A)-> A
\end{lstlisting}

Coefficient-backed structural transforms map the same MATLAB operation over
every local coefficient payload.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {[1 2; 3 4], [10 20; 30 40]}, Degree=1);

vec(A).coeffs(1)
diag(A).coeffs(1)
reshape(A, [1 4]).coeffs(1)
tril(A).coeffs(1)
triu(A, 1).coeffs(1)
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
vec(A).coeffs(1)        -> {[1; 3; 2; 4], [10; 30; 20; 40]}
diag(A).coeffs(1)       -> {[1; 4], [10; 40]}
reshape(A,[1 4]).coeffs(1) -> {[1 3 2 4], [10 30 20 40]}
tril(A).coeffs(1)       -> {[1 0; 3 4], [10 0; 30 40]}
triu(A,1).coeffs(1)     -> {[0 2; 0 0], [0 20; 0 0]}
\end{lstlisting}

For vector payloads, \code{diag(A,k)} constructs an offset diagonal matrix.
\code{reshape} also accepts one inferred empty dimension.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {[1; 2; 3], [4; 5; 6]}, Degree=1);

diag(A, 1).coeffs(1)
reshape(A, [], 1).coeffs(1)
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
diag(A,1).coeffs(1)      -> {[0 1 0 0; 0 0 2 0; 0 0 0 3; 0 0 0 0],
                              [0 4 0 0; 0 0 5 0; 0 0 0 6; 0 0 0 0]}
reshape(A,[],1).coeffs(1)-> {[1; 2; 3], [4; 5; 6]}
\end{lstlisting}

\code{blkdiag} accepts coefficient-backed \code{dpmat} operands and compatible
numeric blocks.  It aligns same-bound grids on a common refinement and elevates
degree as needed.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {1, 2}, Degree=1);
B = dpmat({[0 0.5 1]}, {10, 20, 30}, Degree=1);
C = blkdiag(A, 5, B);

size(C)
C.GridInfo.Vectors{1}
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
size(C)             -> [3 3]
C.GridInfo.Vectors  -> [0 0.5 1]
\end{lstlisting}

\subsection{Display And Plotting}

\code{disp(A)} prints a compact one-line summary.  Plain command-window display
or \code{display(A)} prints matrix size, parameter grid metadata, degree,
physical-cell count, coefficients per cell, continuity, source, and
function-handle status.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {1, 2}, Degree=1);
disp(A)
\end{lstlisting}

Expected output contains:

\begin{lstlisting}[style=dpoutput]
dpmat [1 1] over 1-D grid, degree 1, source coefficient-backed
\end{lstlisting}

\code{plot(A)} samples \code{evaluate} over one or two selected parameter
dimensions and labels each matrix entry in the legend.  For objects with more
than two parameter dimensions, unselected dimensions are fixed at their lower
grid bounds.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, @(rho) [rho, rho^2]);
h = plot(A, SamplesPerCell=4);
numel(h)
\end{lstlisting}

Expected result: \code{numel(h)} is \code{2}, one plotted line for each matrix
entry.  Legends use LaTeX labels such as \(\code{A}_{1,1}\) and the
\(\rho\)-axis label uses LaTeX formatting.

  \caption{One-dimensional \code{dpmat} plot generated from MATLAB.}
  \label{fig:dpmat-plot-1d}
\end{figure}

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1], [10 20]}, @(rho, eta) [rho + eta, rho - eta]);
h = plot(A, [1 2], SamplesPerCell=2, EdgeColor="none");
numel(h)
\end{lstlisting}

Expected result: \code{numel(h)} is \code{2}, one transparent surface for each
matrix entry.  Two-dimensional plotting defaults to \code{FaceAlpha=0.5} unless
the caller supplies a different value, and accepts ordinary graphics options.

The figure files are generated by running \code{doc/generate\_plot\_figures.m}

\subsection{Validation Boundaries}

\code{dpmat} rejects unsupported source types, malformed global coefficient
grids, malformed nested local values, non-finite or complex payloads, bad
function arity, empty or complex function outputs, non-polynomial handles when
explicit Bernstein evidence is requested, and functions that require a higher
\code{Degree} than the caller supplied.  It also rejects constructor attempts to
set \code{IsContinuous}, \code{ContainsDecision}, \code{HasRateDependence}, or
\code{RateBounds}.

Operational errors include out-of-bounds or wrong-dimensional evaluation
points, function-only coefficient algebra or structural transforms,
incompatible matrix sizes, mixed physical grid bounds, \code{cat} dimensions
other than 1 or 2, deletion assignment, matrix-growth assignment, block
assignments with incompatible payload size, invalid reshape sizes, invalid
diagonal or triangular offsets, and invalid plot dimensions or
\code{SamplesPerCell}.

\section{\texorpdfstring{\code{dpvar}}{dpvar} Reference}

\subsection{Purpose}

\code{dpvar} represents continuous degree-1 Bernstein decision variables on a
tensor grid.  Its coefficients are YALMIP \code{sdpvar} matrices stored through
the same \code{dpbase} cell-local layout used by \code{dpmat}.  The current
slice is an affine expression layer; it is not an inequality object and does
not call an SDP solver.

\subsection{Syntax}

\begin{lstlisting}[style=dpmatlab]
P = dpvar(n, gridVectors)
P = dpvar(n, n, gridVectors)
P = dpvar(n, m, gridVectors)
P = dpvar(..., "full")
P = dpvar(..., "symmetric")
P = dpvar(..., RateBounds=rb)
C = P + Q
C = P - Q
C = -P
C = +P
C = P + A
C = A * P
C = P * A
T = P.'
H = P'
B = P(rows, cols)
P(rows, cols) = rhs
C = [P, A]
C = [P; P]
C = blkdiag(P, 1, A)
\end{lstlisting}

Here \code{A} may be coefficient-backed \code{dpmat} data or compatible numeric
data.  Bare affine \code{sdpvar} matrices can also be promoted to constant
coefficient data in supported affine operations.

\subsection{Construction And Continuity}

\begin{lstlisting}[style=dpmatlab]
P = dpvar(2, {[0 1 2]}, "symmetric");

size(P)
P.Degree
P.SourceSummary
first = P.coeffs(1);
second = P.coeffs(2);
numel(getvariables(first{1}))
isequal(getvariables(first{2}), getvariables(second{1}))
\end{lstlisting}

Expected structural outputs:

\begin{lstlisting}[style=dpoutput]
size(P)       -> [2 2]
Degree        -> 1
SourceSummary -> "decision"
variables in first endpoint -> 3
shared boundary handle      -> true
\end{lstlisting}

For a square matrix, \code{dpvar(n, gridVectors)} follows YALMIP's symmetric
default.  Use \code{"full"} when every matrix entry should be an independent
decision variable.  Rectangular matrices are full by construction.

Adjacent physical cells share the YALMIP coefficient handle at their common
boundary.  This is how the current constructor preserves continuity; it does
not add equality constraints.

\subsection{Rate Metadata}

\code{RateBounds} can be supplied as metadata on a \code{dpvar}.  The table has
one row per parameter dimension and lower/upper bounds in columns one and two.
The constructor stores the metadata outside \code{LocalValues}; it does not
enumerate rate vertices.

\begin{lstlisting}[style=dpmatlab]
rb = [-1 2; -3 4];
P = dpvar(1, {[0 1], [10 20]}, RateBounds=rb);

P.HasRateDependence
P.RateBounds
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
HasRateDependence -> true
RateBounds        -> [-1 2; -3 4]
\end{lstlisting}

\subsection{Affine Algebra And Products}

\code{dpvar} supports affine coefficient operations and products where at most
one side contains decision variables.  Products with coefficient-backed known
data use the same Bernstein degree-growth rule as \code{dpmat}.

\begin{lstlisting}[style=dpmatlab]
P = dpvar(1, {[0 1]});
A = dpmat({[0 1]}, {10, 20}, Degree=1);

L = A * P;
R = P * A;

L.Degree
R.Degree
L.ContainsDecision
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
L.Degree        -> 2
R.Degree        -> 2
ContainsDecision-> true
\end{lstlisting}

Same-bound mixed scalar grids are aligned on a common refinement.  Mixed
physical bounds are rejected.  Products such as \code{P * Q}, \code{P * x}
where \code{x} is a bare decision variable, and products involving rate
metadata are rejected in this slice because they would leave the supported
affine SDP expression layer.

\subsection{Matrix Operations And Indexing}

Matrix-like methods report and transform the YALMIP coefficient payloads, not
the number of physical cells.  The supported structural methods mirror the
current \code{dpmat} coefficient-backed methods.

\begin{lstlisting}[style=dpmatlab]
P = dpvar(2, {[0 1]}, "full");

length(P)
height(P)
width(P)
numel(P)
ndims(P)
size(vec(P))
size(diag(P))
size(reshape(P, [1 4]))
size(P(:, end))
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
length(P)          -> 2
height(P)          -> 2
width(P)           -> 2
numel(P)           -> 4
ndims(P)           -> 2
size(vec(P))       -> [4 1]
size(diag(P))      -> [2 1]
size(reshape(P,[1 4])) -> [1 4]
size(P(:,end))     -> [2 1]
\end{lstlisting}

Concatenation, \code{blkdiag}, structural transforms, matrix slicing, and
matrix assignment accept numeric constants, affine \code{sdpvar} blocks, other
compatible \code{dpvar} objects, and coefficient-backed \code{dpmat} blocks.
They reject nonlinear YALMIP expressions, function-only \code{dpmat} operands,
unsupported dimensions, matrix growth, deletion assignment, and incompatible
rate metadata.

\subsection{Validation Boundaries}

\code{dpvar} fixes \code{Degree=1}, \code{IsContinuous=true}, and
\code{ContainsDecision=true} for the public constructor.  Attempts to pass
\code{Degree}, \code{IsContinuous}, \code{ContainsDecision}, or
\code{HasRateDependence} as constructor options are rejected.  A
\code{"symmetric"} structure flag requires a square matrix.  Grid and
\code{RateBounds} validation follows the shared \code{dpbase} rules.

\section{Current Limits}

This repository version intentionally has a narrow public surface.

\begin{itemize}[leftmargin=*]
  \item \code{dpbase}, \code{dpmat}, \code{dpvar}, \code{helper.chk},
        \code{helper.scanMats}, and \code{helper.cell2bern} are implemented and
        covered by the current non-SDP test entry point.
  \item \code{dpmat} is a known-data object only.  It does not contain YALMIP
        decisions, rate dependence, exact function-handle algebra beyond
        evaluation/plot sampling, or solver-facing LMI assembly.
  \item \code{dpvar} is currently a continuous degree-1 YALMIP-backed affine
        expression object.  It does not implement public derivative
        construction, nonlinear decision products, rate-dependent products,
        inequality assembly, or solver calls.
  \item \code{dplmi} remains a future package layer.
  \item There is no public \code{dpdiff} class.  Future derivative behavior is
        expected to belong to \code{dpvar}.
  \item YALMIP modeling, SDP solver invocation, finite rate-vertex assembly,
        and relaxation lemma workflows beyond the current affine \code{dpvar}
        expression layer are not public behavior yet.
  \item Private Bernstein utilities support internal tests and implementation,
        but they are not user-facing functions.
\end{itemize}
