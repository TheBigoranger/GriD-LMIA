\begin{abstract}
This manual describes the current public behavior of the \pkg.  The present
implementation uses \code{dpbase} as the backend parent for cell-local
Bernstein coefficient storage, provides \code{dpmat} for known finite real
matrix data on tensor grids, and provides an initial \code{dpvar} layer for
continuous degree-1 YALMIP-backed decision expressions plus cell-local
rate-weighted derivatives through \code{rhodiff}.  It also provides the first
\code{dplmi} layer: \code{dpvar} comparisons assemble direct coefficient-wise
YALMIP constraints, and \code{toYalmip} exposes them to \code{optimize}.
Relaxation-lemma and Polya workflows remain reserved future extensions.
\end{abstract}

\section{Installation And Verification}

\subsection{Add The Package To The MATLAB Path}

Start \matlab{} in the repository root, or set \code{projectRoot} to the
absolute path of the checked-out repository.  Add the package recursively, then
remove the documentation directory from the executable path.

\begin{lstlisting}[style=dpmatlab]
projectRoot = "path/to/Differential Parameter-Dependent Linear Matrix Inequality";
addpath(genpath(projectRoot));
rmpath(genpath(fullfile(projectRoot, "doc")));
\end{lstlisting}

For local development from the repository root, the shorter form is enough:

\begin{lstlisting}[style=dpmatlab]
addpath(pwd)
\end{lstlisting}

\subsection{Run The Current Test Suite}

The current verification entry point runs the tests for \code{+helper},
\code{@dpbase}, \code{@dpmat}, \code{@dpvar}, and \code{@dplmi}.  The
\code{@dpvar} and \code{@dplmi} tests require YALMIP to be available on the
\matlab{} path.  Solver smoke tests use installed YALMIP solvers; they prefer
MOSEK when available and fall back to \code{lmilab} otherwise.

\begin{lstlisting}[style=dpmatlab]
results = tests.run_all;
table(results)
\end{lstlisting}

Expected result: all currently implemented tests pass.  The suite covers helper
validation, \code{dpbase} construction, grid metadata, local storage, label
ordering, rate-bound validation, and current \code{dpmat} construction,
evaluation, algebra, display, plotting, matrix operations, indexing,
assignment, structural transforms, and error boundaries.  It also covers the
current \code{dpvar} constructor, continuity-by-shared-coefficients behavior,
affine algebra, mixed known/decision products, matrix operations, indexing,
assignment, \code{rhodiff} rate-vertex derivative storage, and validation
boundaries.  The \code{dplmi} tests cover comparison overloads,
coefficient-wise constraint assembly, rate-vertex enumeration, \code{toYalmip},
reserved relaxation/Polya option errors, and small solver-facing smoke
examples.  Full relaxation-lemma assembly, Polya assembly, theorem residual
margins, strictness margins, and solver diagnostics are not implemented yet.

\section{Quick Start}

Most users should start with \code{dpmat} for known parameter-dependent data
and \code{dpvar} for YALMIP-backed decision expressions.  Both classes extend
the shared \code{dpbase} backend, so they expose common grid, cell, label, and
coefficient-inspection methods; ordinary modeling code should not need to
construct raw \code{dpbase} objects.

\subsection{A Known Matrix On A Scalar Grid}

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {2, 4}, Degree=1);

A.MatrixSize
A.Degree
A.SourceSummary
A.evaluate(0.25)
C = A + 5;
C.coeffs(1)
A.cells()
A.lbls()
\end{lstlisting}

Expected structural outputs:

\begin{lstlisting}[style=dpoutput]
MatrixSize =
     1     1

Degree =
     1

SourceSummary =
    "coefficient-backed"

A.evaluate(0.25) -> 2.5
C.coeffs(1)      -> {7, 9}

cells() =
     1

lbls() =
     0
     1
\end{lstlisting}

The expression \code{A + 5} returns another coefficient-backed \code{dpmat} on
the same grid.  The \code{cells}, \code{lbls}, and \code{coeffs} methods come
from the shared \code{dpbase} backend, but the user-facing object remains a
\code{dpmat}.

\subsection{A Known Matrix On A Tensor Grid}

\begin{lstlisting}[style=dpmatlab]

A.GridInfo.Points
A.cells()
A.lbls()

\end{lstlisting}

Expected structural outputs:

\begin{lstlisting}[style=dpoutput]

     0    10
     0    20
     1    10
     1    20

cells() =
     1     1

lbls() =
     0     0
     0     1
     1     0
     1     1

A.coeffs([1 1]) -> {1, 3, 5, 7}
\end{lstlisting}

The first parameter index varies more slowly than the second.  This row order
is used consistently for physical cells and local Bernstein labels across
\code{dpmat} and \code{dpvar}, because both inherit the same backend storage

\subsection{A Function-Backed Known Matrix}

\begin{lstlisting}[style=dpmatlab]
F = dpmat({[0 pi]}, @(rho) sin(rho));

F.SourceSummary
F.evaluate(pi/2)
F.coeffs(1)
\end{lstlisting}

Expected outputs:

\begin{lstlisting}[style=dpoutput]
SourceSummary =
    "function"

F.evaluate(pi/2) -> 1
F.coeffs(1)      -> {0, 0}
\end{lstlisting}

Function-backed \code{dpmat} objects without an explicit \code{Degree} keep the
exact function handle for evaluation.  The inherited local coefficients are
placeholder zeros used only to satisfy shared \code{dpbase} storage; they are
not Bernstein evidence and cannot enter coefficient algebra.

\subsection{A Continuous Decision Variable}

\begin{lstlisting}[style=dpmatlab]

P.MatrixSize
P.Degree
P.IsContinuous
P.ContainsDecision
left = P.coeffs(1);
right = P.coeffs(2);
isequal(getvariables(left{2}), getvariables(right{1}))
\end{lstlisting}

\begin{lstlisting}[style=dpoutput]

     2     2

Degree =
     1

IsContinuous    -> true
ContainsDecision-> true

\end{lstlisting}

\code{dpvar} creates YALMIP decision coefficients on the global grid nodes and
reuses the same coefficient handles in adjacent physical cells.  Continuity is
therefore built into storage; no equality LMI is added by the constructor.

\section{Bernstein And Grid Background}

\subsection{One Cell, Local Coordinates}

On one physical interval \([\rho_0,\rho_1]\), the package uses the normalized
coordinate
\[
  \alpha = \frac{\rho_1-\rho}{\rho_1-\rho_0},
  \qquad 0 \leq \alpha \leq 1.
\]
A degree-\(m\) Bernstein polynomial is written as
\[
  P(\alpha) = \sum_{i=0}^{m} C_i B_i^m(\alpha),
  \qquad
  B_i^m(\alpha) = \binom{m}{i}\alpha^{m-i}(1-\alpha)^i.
\]
For matrix-valued data, each coefficient \(C_i\) is a matrix with the same
payload size.  \code{dpbase} stores those matrices as one flat coefficient
cell for each physical grid cell.

\begin{center}
\begin{tikzpicture}[x=4.2cm,y=2.1cm,>=Latex]

  \draw[fill=black] (0,0) circle (1.3pt) node[below] {$\rho_0$};
  \draw[fill=black] (1,0) circle (1.3pt) node[below] {$\rho_1$};

Degree one is the line-segment case.  It is useful intuition for
piecewise-linear \code{dpmat} data and for the current degree-1 \code{dpvar}
constructor, but Bernstein storage is not limited to splines.

\subsection{Quadratic And Higher-Degree Bases}

For degree two, one cell has three local labels \(0,1,2\):
\[
  P(\alpha) =
  C_0\alpha^2 + 2C_1\alpha(1-\alpha) + C_2(1-\alpha)^2.
\]
The middle coefficient \(C_1\) controls the interior Bernstein basis function,
not an extra physical grid node.  The physical interval still has two endpoints;
the polynomial degree controls how many local coefficient labels live inside
that cell.

The same pattern extends to any degree \(m\).  A cubic cell stores four
coefficient labels \(0,1,2,3\), a quartic cell stores five, and so on.  The
labels are local to the current physical cell; adjacent cells have their own
local coefficient cells even when continuous objects share boundary handles.

\subsection{Products And Degree Growth}

Multiplication is the main reason the package treats Bernstein labels as
coefficient data rather than as samples.  On one cell, multiplying two
degree-1 factors produces a degree-2 polynomial:
\[
\begin{aligned}
  P(\alpha) &= \alpha P_0 + (1-\alpha)P_1,\\
  Q(\alpha) &= \alpha Q_0 + (1-\alpha)Q_1,\\
  P(\alpha)Q(\alpha)
    &= B_0^2 P_0Q_0
     + B_1^2 \frac{P_0Q_1 + P_1Q_0}{2}
     + B_2^2 P_1Q_1.
\end{aligned}
\]

\begin{center}
\begin{tikzpicture}[x=6.2cm,y=1.85cm,>=Latex]
  \draw[->] (-0.04,0) -- (1.08,0) node[right] {$\alpha$};
  \draw[->] (0,-0.08) -- (0,1.55) node[above] {value};
  \draw[gray!30] (0,0) grid[xstep=0.25,ystep=0.25] (1,1.5);
  \draw[blue!65!black,thick] (0,0.25) -- (1,1.30);
  \draw[orange!85!black,thick] (0,1.30) -- (1,0.25);
  \draw[purple!70!black,very thick,domain=0:1,samples=80]
    plot (\x,{(0.25 + 1.05*\x)*(1.30 - 1.05*\x)});
  \draw[purple!45!black,dashed] (0,0.325) -- (0.5,0.876) -- (1,0.325);
  \fill[purple!70!black] (0,0.325) circle (1.4pt)
    node[left] {\scriptsize $P_1Q_1$};

  \node[blue!65!black] at (0.82,1.42) {$P$};
  \node[orange!85!black] at (0.18,1.42) {$Q$};
  \node[purple!70!black] at (0.52,0.48) {$PQ$};
  \node[below] at (0,0) {$0$};
  \node[below] at (1,0) {$1$};
\end{tikzpicture}
\end{center}

The dashed purple control polygon is not another sampled curve.  It marks the
three degree-2 Bernstein coefficients of the product.  The middle coefficient
is higher than the curve value at \(\alpha=1/2\) because the basis function
\(B_1^2(\alpha)=2\alpha(1-\alpha)\) already carries a factor of two.

For general scalar degrees \(n\) and \(m\),
\[
  P(\alpha) = \sum_i P_i B_i^n(\alpha),
  \qquad
  Q(\alpha) = \sum_j Q_j B_j^m(\alpha),
\]
and
\[
  P(\alpha)Q(\alpha) =
  \sum_{k=0}^{n+m} R_k B_k^{n+m}(\alpha),
\]
where
\[
  R_k =
  \sum_{i+j=k} P_iQ_j
  \frac{\binom{n}{i}\binom{m}{j}}{\binom{n+m}{k}}.
\]
This is coefficient convolution with Bernstein binomial normalization.  An
equivalent way to see the same rule, matching the source note
\code{DLMI with Berstain Polynomial.pdf}, is to first absorb the binomial
weights into the coefficient vectors:
\[
  \widehat P_i = \binom{n}{i}P_i,\qquad
  \widehat Q_j = \binom{m}{j}Q_j.
\]
Then the weighted product coefficients are the ordinary discrete convolution
\[
  \widehat R_k
  = (\widehat P * \widehat Q)_k
  = \sum_{i+j=k}\widehat P_i\widehat Q_j,
\]
and the Bernstein coefficients used by the package are recovered by dividing
back by the degree-\(n+m\) binomial weight:
\[
  R_k = \frac{\widehat R_k}{\binom{n+m}{k}}.
\]
For the linear case, the unnormalized convolution is simply
\[
  [P_0,P_1] * [Q_0,Q_1]
  =
  [P_0Q_0,\ P_0Q_1+P_1Q_0,\ P_1Q_1],
\]
and the middle Bernstein coefficient is divided by \(\binom{2}{1}=2\).
For example, if \(P\) has degree two and \(Q\) has degree three, then the
degree-five coefficient with label \(k=2\) is
\[
  R_2 =
  \frac{3}{10}P_0Q_2
  + \frac{6}{10}P_1Q_1
  + \frac{1}{10}P_2Q_0.
\]
This is the binomial-normalized convolution used by coefficient-backed
\code{dpmat} multiplication and by mixed known/decision products that remain
affine in YALMIP variables.

For tensor-product Bernstein polynomials, the same convolution happens over
multi-indices.  If \(p\), \(q\), and \(k\) are local labels, then product
terms contribute only when \(p+q=k\), and the one-dimensional binomial ratios
multiply axis by axis:
\[
  R_k =
  \sum_{p+q=k} P_pQ_q
  \prod_{r=1}^{\ell}
  \frac{\binom{n}{p_r}\binom{m}{q_r}}
       {\binom{n+m}{k_r}}.
\]
Thus two multilinear \(2\times2\) coefficient arrays in two parameters become
one \(3\times3\) degree-2 coefficient array.  This is the tensor version of
the same coefficient convolution, not a multiplication of physical grid
samples.

\subsection{Tensor-Product Labels}

For \(\ell\) parameter dimensions and scalar degree \(m\), each local label is
an \(\ell\)-tuple in \(\{0,\ldots,m\}^{\ell}\).  The number of local
coefficients per physical cell is
\[
  (m+1)^\ell.
\]
For example, \(\ell=2\) and \(m=1\) gives labels
\[
  (0,0),\ (0,1),\ (1,0),\ (1,1),
\]
which is exactly the order returned by \code{obj.lbls()}.

Tensor-product multiplication adds labels component-wise.  In two dimensions,
a label \((i_1,i_2)\) from degree \(n\) and a label \((j_1,j_2)\) from degree
\(m\) contribute to result label
\[
  (k_1,k_2) = (i_1+j_1,\ i_2+j_2),
\]
with a scale factor that is the product of the one-dimensional binomial ratios.
For three parameters, the same rule applies to triples such as
\((i_1,i_2,i_3)+(j_1,j_2,j_3)\).  This is why a degree-1 object over a
three-dimensional parameter grid has \(2^3=8\) local coefficient labels per
physical cell.

\section{\texorpdfstring{\code{dpbase}}{dpbase} Backend Architecture}

\subsection{Purpose}

\code{dpbase} is the shared backend parent class for gridded DP-LMI objects.
\code{dpmat} and \code{dpvar} extend from it: \code{dpmat} adds known numeric
data and exact evaluation, while \code{dpvar} adds YALMIP-backed decision
coefficients and affine expression behavior.  Ordinary user workflows should
construct \code{dpmat} and \code{dpvar}, not raw \code{dpbase} objects.

The purpose of this section is architectural.  It explains why \code{dpmat}
and \code{dpvar} expose the same grid, cell, local-label, coefficient, and
metadata inspection behavior.  The parent class stores tensor-grid metadata,
matrix payload size, Bernstein degree, nested physical-cell coefficient data,
and rate-dependence metadata.

\subsection{Backend Constructor Contract}

The raw constructor is mainly useful for implementation, tests, and reading
the inherited storage contract.  It is not the recommended modeling entry
point.

\begin{lstlisting}[style=dpmatlab]
obj = dpbase(gridVectors, matrixSize, degree)
obj = dpbase(gridVectors, matrixSize, degree, localValues)
obj = dpbase(gridVectors, matrixSize, degree, localValues, Name=Value)
\end{lstlisting}

\subsection{Backend Inputs}

\begin{tabularx}{\linewidth}{@{}>{\raggedright\arraybackslash}p{0.25\linewidth}>{\raggedright\arraybackslash}X@{}}
\toprule
Input & Description \\
\midrule
\code{gridVectors} &
Nonempty cell array of grid node vectors.  Each vector must be finite, real,
strictly increasing, numeric, and contain at least two nodes. \\

\code{1x2} positive integer vector giving the row and column size of every

\end{tabularx}

\subsection{Backend Metadata Options}

\begin{tabularx}{\linewidth}{@{}>{\raggedright\arraybackslash}p{0.3\linewidth}>{\raggedright\arraybackslash}X@{}}
\toprule
Option & Description \\
\midrule
\code{IsContinuous} &
Logical metadata flag.  \code{dpbase} records the flag but does not enforce

\subsection{Inherited Inspection Properties}

All public properties have private set access.  Users normally inspect these
properties through \code{dpmat} or \code{dpvar} objects; they cannot assign to
them after construction.

\begin{tabular}{@{}>{\raggedright\arraybackslash}p{0.32\linewidth}@{\hspace{0.02\linewidth}}>{\raggedright\arraybackslash}p{0.58\linewidth}@{}}
\toprule
Property & Meaning \\
\midrule
\code{GridInfo} &
Struct with fields \code{Vectors}, \code{Points}, \code{Bounds}, and
\code{NumNodes}. \\
\code{MatrixSize} & Matrix payload size stored as a \code{1x2} vector. \\
\code{Degree} & Bernstein degree. \\
\code{LocalValues} &
Nested physical-cell storage.  A tensor grid uses nested brace access, for

\subsection{Backend Local-Storage Example}

The examples below show the parent storage contract for readers who need to
understand inherited behavior or implementation tests.  They are not the
recommended starting point for modeling; use \code{dpmat} for known data and
\code{dpvar} for decision expressions.

For a one-dimensional grid with two physical cells and degree two, each
physical cell stores three local coefficients.

\begin{lstlisting}[style=dpmatlab]
localValues = {{11, 12, 13}, {21, 22, 23}};
obj = dpbase({[0 1 2]}, [1 1], 2, localValues);

obj.coeffs(2)
obj.coeffs({1})
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
obj.coeffs(2)  -> {21, 22, 23}
obj.coeffs({1})-> {11, 12, 13}
\end{lstlisting}

For a tensor grid, physical cells are nested one parameter dimension at a time.
The storage contract is \code{LocalValues\{i1\}\{i2\}...}, not
\code{LocalValues\{i1,i2,...\}}.

\begin{lstlisting}[style=dpmatlab]
mkCoeff = @(offset) {offset+1, offset+2, offset+3, offset+4};
localValues = {
    {mkCoeff(110), mkCoeff(120)}, ...
    {mkCoeff(210), mkCoeff(220)}
    };

obj = dpbase({[0 1 2], [10 20 30]}, [1 1], 1, localValues);
obj.coeffs([2 1])
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
ans =
  1x4 cell array
    {[211]}    {[212]}    {[213]}    {[214]}
\end{lstlisting}

\subsection{Backend Rate Metadata}

\code{dpbase} validates rate bounds and rate-affine coefficient payloads, but it
does not enumerate rate vertices or assemble LMIs.  Public derivative behavior
belongs to \code{dpvar/rhodiff}; solver-facing finite LMI assembly belongs to
\code{dplmi}.

\begin{lstlisting}[style=dpmatlab]
obj = dpbase({[0 1], [10 20]}, [1 1], 0, [], ...
    RateBounds=[-1 1; -2 2]);

obj.HasRateDependence
obj.RateBounds
obj.coeffs([1 1])
\end{lstlisting}

Expected result: \code{HasRateDependence} is true, \code{RateBounds} is the
given \code{2x2} table, and the single local coefficient remains the numeric
zero payload.

Rate-affine payloads use a scalar struct with fields \code{Constant} and
\code{Rate}.  The \code{Rate} field must be a cell array with one matrix per
parameter dimension.

\begin{lstlisting}[style=dpmatlab]
payload = struct("Constant", eye(2), "Rate", {{ones(2), 2*ones(2)}});
localValues = {{{payload}}};
obj = dpbase({[0 1], [10 20]}, [2 2], 0, localValues, ...
    RateBounds=[-1 1; -2 2]);
\end{lstlisting}

The stored coefficient represents the compact form
\[
  C(\dot\rho) =
  C_0 + C_1\dot\rho_1 + C_2\dot\rho_2,
\]
but \code{dpbase} only stores and validates this payload.  It does not solve or
test any inequality involving \(\dot\rho\).

\subsection{Backend Validation And Error Boundaries}

The parent constructor rejects malformed storage inputs early and uses
domain-specific error identifiers.  The following examples are expected to
error:

\begin{lstlisting}[style=dpmatlab]
dpbase([0 1], [1 1], 0)                 % dpbase:InvalidGrid
dpbase({[0 1 1]}, [1 1], 0)             % dpbase:InvalidGridVector
dpbase({[0 1]}, [1 0], 0)               % dpbase:InvalidMatrixSize
dpbase({[0 1]}, [1 1], -1)              % dpbase:InvalidDegree
dpbase({[0 1]}, [1 1], 0, [], ...
    HasRateDependence=true)             % dpbase:InvalidRateBounds
\end{lstlisting}

Ordinary coefficient payloads at the \code{dpbase} layer must be finite, real,
numeric matrices or real two-dimensional \code{sdpvar} matrices matching
\code{matrixSize}.  The parent class validates storage shape only; user-facing
symbolic algebra is defined by \code{dpvar}.

\section{\texorpdfstring{\code{dpmat}}{dpmat} Reference}

\subsection{Purpose}

\code{dpmat} represents known finite real matrix data on a parameter grid.  It
inherits \code{dpbase} storage and adds source handling, exact function
evaluation, coefficient-backed algebra, matrix structural operations, and
two-dimensional block indexing for known data.

\subsection{Syntax}

\begin{lstlisting}[style=dpmatlab]
A = dpmat(gridVectors, source)
A = dpmat(gridVectors, source, Degree=m)
val = A.evaluate(point)
val = evaluate(A, point)
C = A + B
C = A - B
C = -A
C = +A
C = A * B
C = A * M
C = M * A
T = A.'
H = A'
C = [A, B]
C = [A; B]
C = cat(1, A, B)
C = cat(2, A, B)
B = A(rows, cols)
A(rows, cols) = rhs
d = length(A)
d = height(A)
d = width(A)
d = numel(A)
d = ndims(A)
B = squeeze(A)
tf = isequal(A, B)
d = diag(A)

B = reshape(A, [], n)
v = vec(A)
L = tril(A)
L = tril(A, k)
U = triu(A)
U = triu(A, k)

disp(A)
display(A)
h = plot(A)
h = plot(A, dims, SamplesPerCell=n, Name, Value)
\end{lstlisting}

\code{source} can be a function handle, a global cell grid of numeric Bernstein
coefficients, or explicit nested \code{LocalValues} in the \code{dpbase}
contract.

\subsection{Source Modes}

All current \code{dpmat} objects are continuous known data.  Their fixed

\begin{itemize}[leftmargin=*]
  \item \code{IsContinuous=true}
  \item \code{ContainsDecision=false}
  \item \code{HasRateDependence=false}

\subsection{Evaluation}

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {2, 4}, Degree=1);
A.evaluate(0.75)

B = dpmat({[0 1], [10 20]}, {1, 3; 5, 7}, Degree=1);
B.evaluate([0.25, 12.5])

F = dpmat({[0 pi]}, @(rho) sin(rho));
F.evaluate(pi/2)
\end{lstlisting}

Expected outputs:

\begin{lstlisting}[style=dpoutput]
A.evaluate(0.75)        -> 3.5
B.evaluate([0.25 12.5]) -> 2.5
F.evaluate(pi/2)        -> 1
\end{lstlisting}

Coefficient-backed objects evaluate by Bernstein interpolation on the active
physical cell.  Function-backed objects evaluate through the retained exact
handle.  Evaluation points must be finite, real, have one entry per parameter
dimension, and lie inside the grid bounds.

\subsection{Coefficient Algebra}

\code{dpmat} supports coefficient-backed \code{+}, \code{-}, unary \code{-}, and
matrix \code{*}.  Numeric scalars and compatible numeric matrices promote to
constant \code{dpmat} operands.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {1, 2}, Degree=1);
B = dpmat({[0 1]}, {10, 20, 30}, Degree=2);
C = A + B;

C.Degree
C.coeffs(1)
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
C.Degree   -> 2
C.coeffs(1)-> {11, 21.5, 32}
\end{lstlisting}

Multiplication raises Bernstein degree through binomial-normalized local
coefficient convolution.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {[1 2], [3 4]}, Degree=1);
B = dpmat({[0 1]}, {[5; 6], [7; 8]}, Degree=1);
K = A * B;

K.Degree
size(K)
K.coeffs(1)
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
K.Degree   -> 2
size(K)    -> [1 1]
K.coeffs(1)-> {17, 31, 53}
\end{lstlisting}

Same-bound mixed scalar grids are aligned on a common refinement before
coefficient algebra.  Mixed physical bounds are rejected.  Function-only
\code{dpmat} objects are rejected by coefficient algebra until exact
function-handle algebra is designed.

\subsection{Matrix Operations And Indexing}

\code{dpmat} supports transpose, conjugate transpose for real data, horizontal
and vertical concatenation, \code{cat} along dimensions 1 and 2, two-dimensional
matrix slicing, block assignment, matrix-payload shape inspection, and common
structural transforms.  Row and column subscripts support \code{:}, positive
integer vectors, full-length logical vectors, and \code{end}.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {
    [1 2 3; 4 5 6], ...
    [10 20 30; 40 50 60]
    }, Degree=1);

lastCol = A(:, end);
firstRow = A([true false], :);

size(lastCol)
lastCol.coeffs(1)
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
size(lastCol)     -> [2 1]
lastCol.coeffs(1)-> {[3; 6], [30; 60]}
\end{lstlisting}

Assignment accepts numeric constants and compatible \code{dpmat} blocks.  It
does not support deletion assignment, matrix growth, unsupported dimensions, or
coefficient operations on function-only objects.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, {zeros(2), 2*ones(2)}, Degree=1);
A(:, 2) = 5;
A.coeffs(1)
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
A.coeffs(1)-> {[0 5; 0 5], [2 5; 2 5]}
\end{lstlisting}

\subsection{Validation Boundaries}

\code{dpmat} rejects unsupported source types, malformed global coefficient
grids, malformed nested local values, non-finite or complex payloads, bad
function arity, empty or complex function outputs, non-polynomial handles when
explicit Bernstein evidence is requested, and functions that require a higher
\code{Degree} than the caller supplied.  It also rejects constructor attempts to
set \code{IsContinuous}, \code{ContainsDecision}, \code{HasRateDependence}, or
\code{RateBounds}.

Operational errors include out-of-bounds or wrong-dimensional evaluation
points, function-only coefficient algebra or structural transforms,
incompatible matrix sizes, mixed physical grid bounds, \code{cat} dimensions
other than 1 or 2, deletion assignment, matrix-growth assignment, block
assignments with incompatible payload size, invalid reshape sizes, invalid
diagonal or triangular offsets, and invalid plot dimensions or
\code{SamplesPerCell}.

\section{\texorpdfstring{\code{dpvar}}{dpvar} Reference}

\subsection{Purpose}

\code{dpvar} represents continuous degree-1 Bernstein decision variables on a
tensor grid.  Its coefficients are YALMIP \code{sdpvar} matrices stored through
the same \code{dpbase} cell-local layout used by \code{dpmat}.  The current
slice is an affine expression layer.  Comparisons such as \code{P <= 0} and
\code{P >= Q} assemble \code{dplmi} objects, but \code{dpvar} itself does not
choose solvers or call \code{optimize}.

\subsection{Syntax}

\begin{lstlisting}[style=dpmatlab]
P = dpvar(n, gridVectors)
P = dpvar(n, n, gridVectors)
P = dpvar(n, m, gridVectors)
P = dpvar(..., "full")
P = dpvar(..., "symmetric")
P = dpvar(..., RateBounds=rb)
D = rhodiff(P, rb)
D = rhodiff(P)
C = P + Q
C = P - Q
C = -P
C = +P
C = P + A
C = A * P
C = P * A
T = P.'
H = P'
B = P(rows, cols)
P(rows, cols) = rhs
C = [P, A]
C = [P; P]
C = blkdiag(P, 1, A)
K = P <= 0
K = P >= Q
\end{lstlisting}

Here \code{A} may be coefficient-backed \code{dpmat} data or compatible numeric
data.  Bare affine \code{sdpvar} matrices can also be promoted to constant
coefficient data in supported affine operations.

\subsection{Construction And Continuity}

\begin{lstlisting}[style=dpmatlab]

P.SourceSummary

\begin{lstlisting}[style=dpoutput]

SourceSummary -> "decision"
variables in first endpoint -> 3

\end{lstlisting}

For a square matrix, \code{dpvar(n, gridVectors)} follows YALMIP's symmetric
default.  Use \code{"full"} when every matrix entry should be an independent
decision variable.  Rectangular matrices are full by construction.

Adjacent physical cells share the YALMIP coefficient handle at their common
boundary.  This is how the current constructor preserves continuity; it does
not add equality constraints.

\subsection{Rate Metadata}

\code{RateBounds} can be supplied as metadata on a \code{dpvar}.  The table has
one row per parameter dimension and lower/upper bounds in columns one and two.
The constructor stores the metadata outside \code{LocalValues}; it does not
enumerate rate vertices.

\begin{lstlisting}[style=dpmatlab]

P.HasRateDependence
P.RateBounds
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
HasRateDependence -> true
RateBounds        -> [-1 2; -3 4]
\end{lstlisting}

\subsection{\texorpdfstring{Rate-Weighted Derivatives With \code{rhodiff}}{Rate-Weighted Derivatives With rhodiff}}

\code{rhodiff} differentiates a \code{dpvar} with respect to the gridded
parameters and multiplies the local partial derivatives by bounded
\(\dot\rho\) vertices.  The output is another \code{dpvar}, but it is
discontinuous across physical-cell boundaries because each cell keeps its own
local derivative evidence.  This is deliberate: derivative boundary data are
cell-local and are not collapsed into a shared global node.

\begin{lstlisting}[style=dpmatlab]
P = dpvar(1, {[0 2]}, RateBounds=[-2 3]);
D = rhodiff(P);

D.Degree
D.IsContinuous
D.HasRateDependence
D.RateBounds
size(D.coeffs(1))
\end{lstlisting}

Expected structural output:

\begin{lstlisting}[style=dpoutput]
Degree            -> 0
IsContinuous      -> false
HasRateDependence -> true
RateBounds        -> [-2 3]
size(D.coeffs(1)) -> [2 1]
\end{lstlisting}

For this scalar degree-one cell, if \code{c = P.coeffs(1)}, then the two
stored derivative rows are
\[
  -2\,\frac{c_1 - c_0}{2}
  \quad\text{and}\quad
  3\,\frac{c_1 - c_0}{2}.
\]
The denominator is the physical cell width.  In general, a scalar degree
\(m\) cell \([\rho_i,\rho_{i+1}]\) stores
\[
  v\,\frac{m}{h_i}\left(c_{q+1}-c_q\right),
  \qquad q = 0,\ldots,m-1,
\]
for each rate vertex \(v\).  Scalar derivatives of degree \(m>0\) therefore
drop to degree \(m-1\); degree-zero expressions differentiate to zero rows.

For tensor grids, \code{RateBounds} has one row per parameter dimension and
\code{rhodiff} enumerates the Cartesian product of lower/upper bounds.  A
two-parameter grid with bounds \([-1,2]\) and \([-3,5]\) therefore stores four
rate rows in the order
\[
  (-1,-3),\quad (-1,5),\quad (2,-3),\quad (2,5).
\]
The local partial derivatives are accumulated after elevation into a common
tensor Bernstein degree, so a degree-one two-parameter \code{dpvar} returns a
degree-one derivative object with a \code{4x4} coefficient table on each
physical cell.

The supported call forms are \code{rhodiff(P, rb)} and \code{rhodiff(P)}.  The
second form requires \code{P} to carry nonempty \code{RateBounds}.  If explicit
bounds are supplied and \code{P} already carries bounds, the two tables must
match.  Re-differentiating an existing rate-vertex expression is rejected in
this slice.

\subsection{Affine Algebra And Products}

\code{dpvar} supports affine coefficient operations and products where at most
one side contains decision variables.  Products with coefficient-backed known
data use the same Bernstein degree-growth rule as \code{dpmat}.

\begin{lstlisting}[style=dpmatlab]
P = dpvar(1, {[0 1]});
A = dpmat({[0 1]}, {10, 20}, Degree=1);

L = A * P;
R = P * A;

L.Degree
R.Degree
L.ContainsDecision
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
L.Degree        -> 2
R.Degree        -> 2
ContainsDecision-> true
\end{lstlisting}

Same-bound mixed scalar grids are aligned on a common refinement.  Mixed
physical bounds are rejected.  Products such as \code{P * Q}, \code{P * x}
where \code{x} is a bare decision variable, and products involving rate
metadata are rejected in this slice because they would leave the supported
affine SDP expression layer.

Rate-vertex derivative expressions from \code{rhodiff} may still participate
in supported affine operations.  Ordinary \code{dpvar}, numeric, affine
\code{sdpvar}, and coefficient-backed \code{dpmat} operands are broadcast
across the derivative rows when the grids and matrix sizes are compatible.
Products are allowed with numeric or coefficient-backed known data, but
products between two rate-dependent expressions or between a rate-dependent
expression and another decision expression are rejected.

\subsection{Matrix Operations And Indexing}

Matrix-like methods report and transform the YALMIP coefficient payloads, not
the number of physical cells.  The supported structural methods mirror the
current \code{dpmat} coefficient-backed methods.

\begin{lstlisting}[style=dpmatlab]
P = dpvar(2, {[0 1]}, "full");

length(P)
height(P)
width(P)
numel(P)
ndims(P)
size(vec(P))
size(diag(P))
size(reshape(P, [1 4]))
size(P(:, end))
\end{lstlisting}

Expected output:

\begin{lstlisting}[style=dpoutput]
length(P)          -> 2
height(P)          -> 2
width(P)           -> 2
numel(P)           -> 4
ndims(P)           -> 2
size(vec(P))       -> [4 1]
size(diag(P))      -> [2 1]
size(reshape(P,[1 4])) -> [1 4]
size(P(:,end))     -> [2 1]
\end{lstlisting}

Concatenation, \code{blkdiag}, structural transforms, matrix slicing, and
matrix assignment accept numeric constants, affine \code{sdpvar} blocks, other
compatible \code{dpvar} objects, and coefficient-backed \code{dpmat} blocks.
They reject nonlinear YALMIP expressions, function-only \code{dpmat} operands,
unsupported dimensions, matrix growth, deletion assignment, and incompatible
rate metadata.

\subsection{Validation Boundaries}

\code{dpvar} constructor-created variables support \code{Degree=1} by default
and \code{Degree=0} for parameter-independent decision expressions on the same
grid metadata.  Constructor-created variables are continuous decision objects;
those flags are fixed internally.  Attempts to pass the internal continuity,
decision-content, or rate-dependence flags as constructor options are rejected.
A \code{"symmetric"} structure flag requires a square matrix.  Grid and
\code{RateBounds} validation follows the shared \code{dpbase} rules.

\section{\texorpdfstring{\code{dplmi}}{dplmi} Assembly And Solver-Facing Use}

\subsection{Purpose}

\code{dplmi} wraps the finite YALMIP constraints produced from cell-local
\code{dpvar} residuals.  In the current implementation, \code{dpvar <= rhs}
and \code{dpvar >= rhs} first form an affine residual using the supported
\code{dpvar} algebra, then assemble one semidefinite constraint for every
physical cell, every local Bernstein coefficient, and every active
\(\dot\rho\) rate-vertex row.

The current \code{dplmi} layer is deliberately direct: it constrains every
stored Bernstein coefficient.  Relaxation-lemma and Polya options are accepted
as named options only so unsupported requests can fail clearly.

\subsection{Syntax}

\begin{lstlisting}[style=dpmatlab]
C = P <= Q
C = P <= 0
C = P >= Q
C = P >= eye(n)
C = dplmi(expr, "<=")
C = dplmi(expr, ">=", relaxLemma=false, UsePolya=false, PolyaDegree=0)
F = toYalmip(C)
F = C.toYalmip()
\end{lstlisting}

Here \code{expr} must be a \code{dpvar} residual.  The comparison overloads are
usually the most convenient entry point because they reuse existing \code{dpvar}
promotion rules for numeric constants, affine \code{sdpvar} matrices,
coefficient-backed \code{dpmat} operands, and compatible \code{dpvar} objects.

\subsection{Direct Coefficient Constraints}

The simplest use is a coefficient-wise matrix inequality over a grid.

\begin{lstlisting}[style=dpmatlab]
P = dpvar(2, {[0 1 2]}, "symmetric");
Cpos = P >= eye(2);

class(Cpos)
numel(Cpos.Constraints)
Cpos.RelaxLemma
Cpos.UsePolya
Cpos.PolyaDegree
\end{lstlisting}

Expected structural output:

\begin{lstlisting}[style=dpoutput]
class(Cpos)           -> "dplmi"
numel(Cpos.Constraints) -> 4
RelaxLemma           -> false
UsePolya             -> false
PolyaDegree          -> 0
\end{lstlisting}

There are two physical cells and two degree-one local coefficients per cell,
so direct assembly creates four scalar YALMIP semidefinite constraint entries.
The entries remain inspectable in \code{Cpos.Constraints}; use
\code{toYalmip(Cpos)} only at the solver boundary.

\subsection{Rate-Vertex Assembly From \texorpdfstring{\code{rhodiff}}{rhodiff}}

When the residual contains \code{rhodiff(P, rb)}, each local coefficient table
has one row per admissible \(\dot\rho\) vertex.  \code{dplmi} constrains every
row.

\begin{lstlisting}[style=dpmatlab]
P = dpvar(2, {[0 1 2]}, "symmetric", RateBounds=[-1 1]);
D = rhodiff(P);
Cdecay = D <= 0;

D.Degree
size(D.coeffs(1))
numel(Cdecay.Constraints)
\end{lstlisting}

Expected structural output:

\begin{lstlisting}[style=dpoutput]
D.Degree                 -> 0
size(D.coeffs(1))        -> [2 1]
numel(Cdecay.Constraints)-> 4
\end{lstlisting}

The grid has two physical cells.  The scalar rate interval \([-1,1]\) has two
vertices.  The degree-one derivative drops to degree zero, so each cell has one
local derivative coefficient per rate vertex: \(2\) cells times \(2\) rate rows.

For a two-parameter grid, the same rule applies to the tensor product of rate
vertices:

\begin{lstlisting}[style=dpmatlab]
rb = [-1 1; -2 2];
P = dpvar(2, {[0 1], [0 1]}, "symmetric", RateBounds=rb);
D = rhodiff(P);
C = D <= 0;

size(D.coeffs([1 1]))
numel(C.Constraints)
\end{lstlisting}

Expected structural output:

\begin{lstlisting}[style=dpoutput]
size(D.coeffs([1 1])) -> [4 4]
numel(C.Constraints)  -> 16
\end{lstlisting}

There is one physical cell, four rate vertices, and four degree-one tensor
coefficients after multivariate partial derivatives are elevated into a common
tensor basis.

\subsection{A Lyapunov-Style Solver Smoke Test}

The following example mirrors the current solver smoke test.  It compares a
constant decision matrix against a parameter-dependent one for the same
coefficient-wise decay inequality.

\begin{lstlisting}[style=dpmatlab]
A = dpmat({[0 1]}, @(x) (1 - x) * [-1 -1; 1 -1] ...
    + x * [-1 -10; 0.1 -1], Degree=1);
opts = sdpsettings('verbose', 0);

Pc = dpvar(2, {[0 1]}, Degree=0);
Cdecay = Pc * A + A' * Pc <= -1e-10 * eye(2);
Cpos = Pc >= eye(2);
solConst = optimize([Cdecay.toYalmip, Cpos.toYalmip], [], opts);

Pd = dpvar(2, {[0 1]});
Cdecay = Pd * A + A' * Pd <= -1e-10 * eye(2);
Cpos = Pd >= eye(2);
solDp = optimize([Cdecay.toYalmip, Cpos.toYalmip], [], opts);

[solConst.problem, solDp.problem]
\end{lstlisting}

Expected result under MOSEK:

\begin{lstlisting}[style=dpoutput]
[solConst.problem, solDp.problem] -> [1 0]
\end{lstlisting}

YALMIP returns \code{problem=1} for the constant-\(P\) infeasible case and
\code{problem=0} for the degree-one parameter-dependent feasible case in the
current local MOSEK test setup.  When MOSEK is unavailable, the smoke test
falls back to \code{lmilab} and checks the solver-dispatch path without using
LMILAB to certify this infeasibility distinction.

\subsection{A Block DP-LMI With A Performance Variable}

This example is adapted from the root \code{test.m} case.  The test suite keeps
the same block structure in a reduced-grid \code{dplmi} solver-smoke test; the
manual version below keeps the original 20-point grid.  It combines known
parameter-dependent matrices, a rate-weighted derivative, a scalar degree-zero
performance variable, block matrix assembly, and solver-backed optimization.

\begin{lstlisting}[style=dpmatlab]
grid = linspace(0, 1, 20);
A = dpmat(grid, @(x) [-1, 0.5; -1, -2] ...
    + x * [-1.3, -20; 2, -10], Degree=1);
B = dpmat(grid, @(x) [1, -4; -1, -1] ...
    + x * [2.2, 0.5; -6, -5], Degree=1);
C = eye(2);
D = zeros(2);

P = dpvar(2, grid);
diffP = rhodiff(P, [-1 1]);
gamma = dpvar(1, grid, Degree=0);

E1 = [diffP + P * A + A' * P, P * B, C';
    B' * P, -gamma * eye(2), D';
    C, D, -gamma * eye(2)] <= 0;
E2 = P >= 0;

numel(E1.Constraints)
numel(E2.Constraints)

if exist('mosekopt', 'file') ~= 0
    opts = sdpsettings('solver', 'mosek', 'verbose', 0);
else
    opts = sdpsettings('solver', 'lmilab', 'verbose', 0);
end
objective = gamma.LocalValues{1}{1};
sol = optimize([E1.toYalmip, E2.toYalmip], objective, opts);
value(objective)
\end{lstlisting}

Expected structural output before the solver call:

\begin{lstlisting}[style=dpoutput]
numel(E1.Constraints) -> 114
numel(E2.Constraints) -> 38
\end{lstlisting}

The first block inequality has \(19\) physical intervals, degree-two residual
coefficients, and two rate vertices from \code{diffP}, so it produces
\(19 \times 3 \times 2 = 114\) direct constraints.  The positivity constraint
has \(19\) intervals and two degree-one coefficients, so it produces
\(19 \times 2 = 38\) constraints.  The final numeric value depends on the
installed solver and tolerances; the test verifies a successful solve and a
finite objective value, using MOSEK when available and \code{lmilab} otherwise.

\subsection{Validation Boundaries}

\code{dplmi} requires square symmetric or Hermitian coefficient matrices.
Non-square residuals fail with \code{dplmi:InvalidMatrixSize}; non-symmetric
residuals fail with \code{dplmi:NonSymmetricExpression}.  Unsupported
relaxation and Polya requests fail explicitly:

\begin{lstlisting}[style=dpmatlab]
P = dpvar(2, {[0 1]}, "symmetric");

dplmi(P, "<=", relaxLemma=true)  % dplmi:UnsupportedRelaxLemma
dplmi(P, "<=", UsePolya=true)    % dplmi:UnsupportedPolya
dplmi(P, "<=", PolyaDegree=1)    % dplmi:UnsupportedPolya
\end{lstlisting}

Direct coefficient-wise assembly is the only implemented route in this slice.
Strictness margins, theorem residual margins, relaxation slacks, Polya
lifting, diagnostics, and high-level solver wrappers remain future work.

\section{Current Limits}

This repository version intentionally has a narrow public surface.

\begin{itemize}[leftmargin=*]
  \item The backend parent \code{dpbase}, user-facing \code{dpmat} and
        \code{dpvar} classes, \code{helper.chk}, \code{helper.scanMats}, and
        \code{helper.cell2bern} are implemented and covered by the current
        MATLAB test entry point.
  \item \code{dpmat} is a known-data object only.  It does not contain YALMIP
        decisions, rate dependence, exact function-handle algebra beyond
        evaluation/plot sampling, or solver-facing LMI assembly.
  \item \code{dpvar} is currently a continuous degree-1 YALMIP-backed affine
        expression object with \code{rhodiff} support for discontinuous
        cell-local rate-vertex derivatives.  It does not implement nonlinear
        decision products, products with rate dependence on both sides, or
        solver calls.
  \item \code{dplmi} implements direct coefficient-wise finite YALMIP
        constraint assembly from \code{dpvar} residuals.  It does not yet
        implement relaxation-lemma assembly, Polya assembly, strictness
        margins, residual evidence, diagnostics, or high-level solver wrappers.
  \item There is no public \code{dpdiff} class.  Public derivative behavior
        belongs to \code{dpvar} through \code{rhodiff}.
  \item YALMIP solver invocation is available through ordinary YALMIP calls
        after converting \code{dplmi} objects with \code{toYalmip}; this package
        does not yet provide a custom solver wrapper.
  \item Private Bernstein utilities support internal tests and implementation,
        but they are not user-facing functions.
\end{itemize}
