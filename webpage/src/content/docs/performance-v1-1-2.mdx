Documentation v1.1.2 describes a substantial internal rewrite with a largely
compatible modeling interface. Operation-local numeric plans are built once
and reused for Bernstein elevation and normalized coefficient products.
Direct and Pólya assembly preallocate in the established
cell/rate-row/coefficient/column-major order. Gram certificates reuse numeric
coefficient maps while allocating fresh independent Gram variables for every
required block. `toYalmip` concatenates retained constraints once.

The rewrite preserves the represented function, decision-variable identities,
selected certificate family, constraint and cone order, and exact coefficient
identities, up to scale-appropriate floating-point summation differences.

## Transient Validation Mode

```matlab
A = pdmat([0 1], {1, 2}, Degree=1, ValidationMode="STRICT");
P = pdvar(1, [0 1], ValidationMode="fast");
C = pdlmi(P, ">=", ValidationMode="strict");
C = C.applyPolya(0, ValidationMode="FAST");
hasStoredMode = isprop(A, "ValidationMode")
```

```text
hasStoredMode =
  logical
   0
```

`ValidationMode` accepts case-insensitive scalar text `"fast"` or `"strict"`
and defaults to `"fast"`. It is local to each constructor or certificate
selection call, is not stored, and is not inherited by later algebra or
selection calls.

In normalized algebra and certificate paths, fast mode samples repeated
post-normalization structural checks; strict mode checks every generated cell,
rate row, coefficient payload, plan application, and Gram-map application.
Both modes retain public option, compatibility, continuity, affine-safety,
inequality-classification, and actual constraint-generation checks. The raw
developer-facing `pdbase` constructor is the deliberate exception: fast mode
checks repeated coefficient structure only in the first supplied physical
cell, while strict mode audits every supplied cell.

## Measured Workloads

The benchmark functions warm every timed operation, build setup objects outside
the timed bodies, verify equivalence first, and report the median of three
independent `timeit` estimates. These are contention-free observations from
one MATLAB R2026a Update 3 run on the current machine, not performance
guarantees.

| Benchmark | Workload | Operation | Median | Captured-baseline comparison |
| :--- | :--- | :--- | ---: | ---: |
| Stage 1B | 2 parameters, 16 cells, degree 3, `3x3` | numeric multiplication | 0.045856 s | 2.01x |
| Stage 1B | same | known x affine multiplication | 0.744692 s | 1.90x |
| Stage 1B | same | numeric `elevate(+2)` | 0.004389 s | 3.19x |
| Stage 1B | same | symbolic `elevate(+2)` | 0.117991 s | not supplied |
| Stage 1C | 2 parameters, 16 cells, degree 3, `3x3`; Direct 256 / Pólya 400 constraints | Direct assembly, fast | 0.090959 s | 2.51x |
| Stage 1C | same | Direct assembly, strict | 0.153322 s | not supplied |
| Stage 1C | same | Pólya `+1`, fast | 0.242357 s | not supplied |
| Stage 1C | same | Pólya `+1`, strict | 0.376200 s | not supplied |
| Stage 1C | same | Direct `toYalmip` | 0.155284 s | 0.91x |
| Stage 1C | same | Pólya `toYalmip` | 0.271730 s | not supplied |
| Stage 2 | 2 parameters, 1 cell, degree 2, `2x2`, plus scalar/interval variants | FullBox 2-D, fast | 0.053643 s | 5.61x |
| Stage 2 | same | FullBox 2-D, strict | 0.051391 s | not supplied |
| Stage 2 | same | Putinar 2-D | 0.046707 s | not supplied |

The `0.91x` Direct export observation means this run was slower than its
captured baseline; it is not evidence that every optimized path improved.

## Reproduce

```matlab
tests.benchmark_stage1b_performance()
tests.benchmark_stage1c_performance()
tests.benchmark_stage2_performance()
```

Run `tests.run_all()` before interpreting timings. Benchmark results depend on
machine load, MATLAB/YALMIP versions, JIT state, and solver-independent
allocation behavior.
